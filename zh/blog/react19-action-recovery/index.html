React19表单交互：乐观更新、失败恢复与服务端约定

利用 Actions、useActionState 和 useOptimistic 表达提交过程，同时保留草稿、区分未知结果与业务冲突，并用稳定操作键控制失败后的重试。

xq.Xiaofeng Qiao发布于 2026年10月23日本文暂时仅提供中文版本。

更少的 loading 代码，并不自动带来可靠保存

表单提交后立刻把新名字放进列表，会让界面感觉很快。随后接口失败，临时行应该怎样撤回？用户输入是否还在？如果服务端其实已经保存，只是响应丢了，再点一次会不会创建两条记录？这些问题不会因为换成新 Hook 就消失。

React 19 在 2024 年 12 月正式稳定，Actions、useActionState、useOptimistic 与表单协作是其中的重要能力。本文以这个稳定版本提供的基础接口为回顾范围，使用今天编写的独立分析示例；当前文档中的后续扩展不作为 2024 年已经存在的依据。React 19 发布记录

先把三个层次分开

用户正在编辑的草稿、请求期间的乐观显示、服务端确认的记录，是三份含义不同的数据。草稿应由明确的输入状态持有；乐观行应标为“保存中”；只有有效回执才能进入已确认记录。若把临时行直接塞进持久列表，再靠错误分支删回来，很容易漏掉一个失败路径。

useActionState 把 Action 的结果与 pending 状态连接到组件。Action 函数接收的第一个参数是前一次状态，后面才是提交载荷；直接把原本只接收 FormData 的函数塞进去，可能读错参数。useActionState 参数约定

这里的 Action 是客户端函数，它调用注入的 save 接口。把函数放进 <form action> 不会自动创建数据库事务或服务器鉴权。框架的 Server Function 还涉及部署与服务端边界，不应和普通客户端 Action 混为一谈。表单 Action 与 Server Function

用结构化结果表达恢复路径

下面的动作函数先验证输入，再发布临时显示，最后检查回执。教学接口约定：成功保存标准化后的姓名，并返回非空字符串编号；若服务端另做规范化，接口还应返回最终姓名，界面据此更新。

function makeSaveAction(save, onOptimistic = () => {}) {
  return async function action(previous, formData) {
    if (!formData || typeof formData.get !== 'function') {
      return { kind: 'invalid', message: '表单结构错误' };
    }
    const rawName = formData.get('name');
    const rawKey = formData.get('requestKey');
    if (typeof rawName !== 'string' || typeof rawKey !== 'string') {
      return { kind: 'invalid', message: '请检查输入类型' };
    }
    const name = rawName.trim(), requestKey = rawKey.trim();
    if (!name || name.length > 80
        || !/^[a-zA-Z0-9_-]{8,128}$/.test(requestKey)) {
      return { kind: 'invalid', message: '请检查姓名和操作标识' };
    }
    onOptimistic({ name, requestKey });
    try {
      const receipt = await save({ name, requestKey });
      if (!receipt || typeof receipt.id !== 'string' || !receipt.id) {
        return { kind: 'uncertain', message: '结果未确认，请用同一操作重试' };
      }
      return { kind: 'saved', receipt: { id: receipt.id, name, requestKey } };
    } catch (error) {
      if (error && error.code === 'version_conflict') {
        return { kind: 'conflict', message: '资料已有更新，请先核对' };
      }
      if (error && error.code === 'request_conflict') {
        return { kind: 'request_conflict', message: '操作标识已用于其他内容，请核对' };
      }
      return { kind: 'uncertain', message: '结果未确认，请用同一操作重试' };
    }
  };
}

返回“结果未确认”是刻意的。网络错误和错误格式的响应，都不足以证明服务端没有保存。操作键应在一次业务意图开始时产生，重试继续使用它；服务端也必须真实实现同键去重和同键异参拒绝。前端隐藏字段不是鉴权凭证，服务器仍要校验用户、权限、字段与操作作用域。

业务版本冲突则需要读回最新状态，让用户合并或确认；它不属于无条件重试。也不要仅按所有 HTTP 409 返回同一个错误：版本冲突、操作键异参和其他业务拒绝，需要接口适配层提供稳定的错误类别。

乐观状态应随着 Action 收束

以下是组件里的核心连接，saved 是已确认记录：

const [saved, setSaved] = useState([]);
const [rows, addOptimistic] = useOptimistic(saved, (current, entry) =>
  current.some(row => row.requestKey === entry.requestKey)
    ? current : current.concat({ ...entry, pending: true })
);
const [result, submit, pending] = useActionState(async (previous, data) => {
  const next = await makeSaveAction(save, addOptimistic)(previous, data);
  if (next.kind === 'saved') {
    startTransition(() => setSaved(current =>
      current.some(row => row.id === next.receipt.id)
        ? current : current.concat(next.receipt)
    ));
  }
  return next;
}, { kind: 'idle' });

这些语句放在函数组件内，相关函数从 React 导入；表单使用 action={submit}，渲染 rows 时把 pending 行显示成保存中。乐观更新发生在 Action 的上下文内，Action 结束后回到已确认的基础数据；失败时不把临时记录转成事实，成功时则用回执更新基础列表。useOptimistic 的值与 Action 范围

这里用 startTransition 包住 await 后更新另一份组件状态的步骤，避免把异步边界后的更新身份想当然。组件还需受控输入、列表渲染和错误提示；这段是连接逻辑，不是已运行的完整 UI。若回执代表的是更新既有记录，应按编号替换对应项，而不是套用本例“新建记录”的追加操作。

草稿保留要显式设计

函数式表单 Action 成功后，React 会重置非受控字段。不能先把所有业务错误都包装成普通返回值，又未经验证地假设输入框一定保留。本文选择受控输入，将姓名放在独立的草稿状态里；只有收到确认成功或用户主动选择新建下一条时才清理草稿。表单重置行为

提交期间可以暂时冻结字段，保证屏幕内容和提交快照一致；长表单若要继续编辑，就要另外保存“提交版本”和“新草稿”，避免旧响应覆盖新编辑。成功后新建下一条才换新操作键，失败重试则保留原键。按钮禁用只是交互保护，不能替代服务端幂等。

共享按钮若使用 useFormStatus，必须作为目标 <form> 的后代渲染，才能读取那张表单的 pending；在创建表单的同一个外层组件里读它，不能指望它自动感知自己稍后返回的子表单。useFormStatus 的父表单范围

多个提交入口仍需要同一份业务协议

一个表单的 pending 或 Action 队列，管不到另一个标签页、另一台设备或后台任务。即使浏览器界面限制了重复点击，服务端仍要依据业务键和版本判断并发；乐观列表的去重也应使用稳定编号或请求键，不能依赖数组下标代表同一次操作。

尤其要处理“结果未知以后又修改了内容”。这时复用原操作键发送另一份数据，应该得到明确的异参冲突；直接换新键再点保存，也可能在原请求已经成功时创建第二条记录。更合适的交互是先查询原请求结果，再由用户决定修改既有记录或开始新的业务意图。界面需要把这条路径说清楚，而不只是提供一个含义模糊的重试按钮。

错误提示也应绑定对应的提交快照。用户已经修改姓名后，旧快照的字段错误不应继续像当前校验结果一样展示。可以在编辑时撤下过期的字段提示，同时保留尚未解决的全局冲突说明。保存中与失败状态使用清楚的文字及适当的 aria-live 通知；第一处可修正错误应能由键盘定位，不能只靠颜色变化解释结果。

验证动作契约，再验证真实表单

随稿 examples/react19_action.mjs 在 Node.js 16.16.0 执行八组行为检查，覆盖标准化成功、无效字段不调用保存、非文本载荷拒绝、空表单结构拒绝、业务版本冲突、第一次响应丢失后同键重试只接受一次、无效回执被标为未知，以及只为有效提交产生临时条目。

这是注入模拟 save 与类 FormData 读取器的动作函数测试，没有加载 React 19 渲染器，不能证明 pending、表单自动重置或乐观状态回退已在浏览器正确运行。实际集成还要验证双击、键盘提交、慢响应、组件卸载、受控字段保留、错误焦点和重复回执去重。未接通真实后端时，也不能把模拟收据说成真实保存。

结论

React 19 减少了描述提交过程的样板代码，但业务可靠性仍来自清楚的草稿归属、临时状态、确认回执和重试契约。把“看起来已经完成”与“已经得到服务端确认”分开，乐观交互才能既快又能恢复。
