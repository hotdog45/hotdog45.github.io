React Native混合接入：桥接协议、批量更新与原生边界

回顾旧Bridge时代的混合应用，用有界采样模型解释哪些事件可以合并、何时需要背压，以及导航和会话为何应有单一所有者。

xq.Xiaofeng Qiao发布于 2026年10月23日本文暂时仅提供中文版本。

共用一套界面之前，先共用一套约定

在已有iOS和Android应用里接入RN，难点往往不是把一个组件显示出来，而是让它服从现有导航、会话和发布流程。JS希望打开页面，原生发现登录已过期；JS还在处理一串滚动事件，原生页面已经退出。跨端界面可以共用实现，并不代表两侧可以各自维护一份不受约束的真实状态。

本文在2026年回顾2016年的混合接入问题，讨论旧Bridge的异步与序列化边界，不把JSI、TurboModules或新架构写成当年能力。RN在2015年发布Android支持，2016年官方活动回顾已经专门讨论既有代码库、原生导航所有权和跨平台API的取舍。Android发布记录 2016年官方回顾

可以把首个模块限定为“原生商品列表进入RN筛选页，返回筛选条件，再由原生刷新列表”。原生拥有导航与登录状态，RN拥有筛选交互的临时状态。两侧交换条件，而不是互相持有对方的页面对象或任意执行代码。这样出现问题时，能明确判断是入口、消息还是业务状态出了差异。

一次跨边界调用不是一次本地函数调用

旧架构通过异步Bridge在JS和原生之间传递序列化调用。今天官方的新架构介绍回顾了这一路径及高频、大对象通信带来的约束；这份后来的说明适合解释机制，不代表它描述的新功能在2016年已经存在。官方架构回顾

设计API时，调用方不能假定拿到原生返回值后，所有依赖的界面变化已经显示；也不能把跨边界对象当成两侧共享的可变内存。发送的数据越宽，参数版本和兼容性越难管理。传一个业务ID和必要上下文，通常比传完整对象图更容易检查，但原生或服务端仍要验证ID是否属于当前用户。

平台差异也不一定要全部隐藏。两个平台的选择器、权限提示和返回键语义可能不同。一个包含几十个可选参数的“统一API”，有时只是把差异推迟到了运行时。可以共享业务请求与结果模型，同时为确实不同的交互保留平台适配层。边界越小，双端实现越容易采用同一组契约用例。

合并的是可替换状态，不是业务命令

滚动位置、拖动预览等高频采样，通常只需要最新值；提交订单、删除草稿或审计事件却不能随便丢掉中间操作。首先判断一条消息表达的是“当前是什么”，还是“必须发生一次什么”。把两者放进同一条无界事件队列，容易同时产生延迟和难以解释的丢事件。

下面的完整Node程序只模拟可替换UI采样：同一view的待发送值合并为最新值，最多保留两个view，每次只允许一批未确认消息。确认携带页面修订号和序号，页面重置后旧确认失效。这里的上限是演示参数，不是RN Bridge的固定容量。

'use strict';
var assert = require('assert');

// A transport model for replaceable UI samples, not RN bridge implementation.
function Sampler(send, maxItems) {
  this.send = send;
  this.maxItems = maxItems;
  this.pending = Object.create(null);
  this.revision = 1;
  this.sequence = 0;
  this.inFlight = 0;
}
Sampler.prototype.sample = function (viewId, value) {
  if (typeof viewId !== 'string' || viewId.length === 0 || viewId.length > 64 ||
      !Number.isFinite(value)) return false;
  if (!Object.prototype.hasOwnProperty.call(this.pending, viewId) &&
      Object.keys(this.pending).length >= this.maxItems) return false;
  this.pending[viewId] = value;
  return true;
};
Sampler.prototype.flush = function () {
  if (this.inFlight || !Object.keys(this.pending).length) return null;
  var events = this.pending;
  this.pending = Object.create(null);
  var message = { revision: this.revision, sequence: ++this.sequence, events: events };
  this.inFlight = message.sequence;
  this.send(JSON.parse(JSON.stringify(message)));
  return message;
};
Sampler.prototype.ack = function (revision, sequence) {
  if (revision !== this.revision || sequence !== this.inFlight) return false;
  this.inFlight = 0;
  return true;
};
Sampler.prototype.reset = function () {
  this.revision += 1;
  this.pending = Object.create(null);
  this.inFlight = 0;
};

var sent = [];
var sampler = new Sampler(function (message) { sent.push(message); }, 2);
for (var i = 0; i < 100; i += 1) sampler.sample('list-A', i);
var first = sampler.flush();
assert.strictEqual(sent.length, 1);
assert.strictEqual(sent[0].events['list-A'], 99);
sampler.sample('list-A', 101);
assert.strictEqual(sampler.flush(), null);
assert.strictEqual(sampler.ack(first.revision, first.sequence + 1), false);
assert.strictEqual(sampler.ack(first.revision, first.sequence), true);
var second = sampler.flush();
assert.strictEqual(second.events['list-A'], 101);
sampler.reset();
assert.strictEqual(sampler.ack(second.revision, second.sequence), false);
assert.strictEqual(sampler.sample('a', 1), true);
assert.strictEqual(sampler.sample('b', 2), true);
assert.strictEqual(sampler.sample('c', 3), false);
assert.strictEqual(sampler.sample('a', NaN), false);
assert.strictEqual(sampler.sample('', 1), false);
assert.strictEqual(sampler.sample(new Array(66).join('a'), 1), false);
console.log('PASS: 13 batching/backpressure/revision assertions; synthetic transport only');

合并发生在发送之前，而不是在原生已经执行操作后再假装它没发生。JSON.stringify与反序列化在这里用于让测试中的发送端和接收端没有共享对象引用，并不声称复刻RN内部完整传输格式。代码在Node 16.16.0执行，验证的是消息契约模型，没有启动RN运行时。

容量还要考虑单条内容，而不仅是条数。示例只接受有限数值，并把view标识限制为64个字符；若实际接口允许传图片Base64、完整列表或任意字符串，即使一批只有两项也可能很重。此时应另设字节预算、分片协议或改传本地资源标识。调试日志也不应把大payload再完整复制一遍，否则观察消息的成本可能掩盖原来的瓶颈。

背压需要结束条件，也需要失败策略

模型中没有收到确认就不会继续发送，因此待确认批次不能无限累积。但生产系统还要决定确认丢失、页面销毁和原生异常时怎么办。对于可替换采样，可以在超时后结束该修订，重新同步一份完整当前状态；不能直接把这一策略用于支付或订单命令，否则重发会引入重复副作用。

另一个容易忽略的地方是事件监听。进入页面注册监听，退出页面却没有对应移除，即使业务对象没有明显引用环，也可能收到重复事件。会话失效时原生应能接管流程，JS也要拒绝旧页面的后续状态提交。仅传一个页面名称不够，同名页面可以多次进入，修订号或独立实例ID才有助于区分。

队列有界不代表体验一定顺畅。合并到最后一个位置，会改变中间动画的观察效果；如果交互本身需要每个采样点，例如轨迹绘制，就必须采用不同的采样、压缩或原生处理方案。判断是否允许合并，应来自业务语义和视觉验收，而不是先决定“所有消息都节流100毫秒”。

用兼容矩阵检查混合发布

混合应用还有两份变更需要一起审查：原生宿主版本与JS bundle版本。新增一个原生方法后，旧宿主可能尚未具备它；更新JS代码却只在最新原生包上测试，会把这个问题留给仍运行旧版本的用户。应显式记录方法版本和能力探测，在缺少能力时走可理解的旧流程，而不是吞掉异常显示成功。

本例用 node --check rn_bridge_boundaries.js 检查语法，再运行脚本。十三组断言覆盖最新值合并、待确认时不继续发送、错误确认、正确确认、旧页面确认、队列容量、标识长度和非有限数拒绝。测试中一百次采样合成一批，这是输入fixture的结果，不能据此宣传真实应用性能提升百分比。

测试之外可以记录每条业务流程的发送批次、payload字节数、等待确认时间与丢弃原因，但不要把这些日志直接当成用户可见延迟。一次操作还可能等待JS计算、原生布局、网络或渲染；应关联同一流程的时间点，再决定是否值得调整边界。

真实集成验收应分别覆盖iOS和Android，在两种宿主版本下检查进入退出、登录过期、快速重复进入和后台返回。再用真实设备分析JS、原生主线程与通信负载，确定卡顿在哪一侧。迁移的价值不是跨边界调用次数看起来少了，而是每条消息都有清楚的含义、容量和生命周期，两个平台也能对相同失败给出一致的业务结果。
