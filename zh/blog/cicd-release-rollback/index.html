CI/CD可回退发布：构建产物、配置校验与验收门槛

围绕同一份不可变产物建立验证链，区分构建成功、发布切换、业务验收和可安全回退的范围。

xq.Xiaofeng Qiao发布于 2026年10月23日本文暂时仅提供中文版本。

流水线全绿，为什么还不能叫发布成功

一次静态站点发布可以经历这些步骤：编译成功、压缩包上传成功、服务器目录切换成功。用户仍可能打开空白页，因为资源路径错误，或配置引用了不存在的 API。

流水线的每一步都可能正确完成自己负责的动作，却没有覆盖用户真正需要的结果。本文以 2021 年的持续交付问题为回顾视角，使用 2026 年编写的本地发布模型，讨论如何把构建、部署和验收连接起来。示例只操作临时目录，没有访问服务器或更改任何在线服务。

每个环境都重新构建，会破坏证据链

如果测试环境和生产环境分别安装依赖、分别构建，即使提交号相同，最终文件也可能不同。依赖源变化、未锁定版本、构建时变量或工具链差异，都能改变产物。

更清楚的流程是构建一次，保存产物清单、提交标识、工具链和内容摘要，随后提升同一份产物。配置如果必须随环境变化，应作为明确的独立输入管理，并在上线前校验必需字段及允许值。不要把数据库密码或生产密钥写进浏览器可下载的构建产物。

哈希可以检查产物是否与先前记录一致，但不能证明它本身可信。如果攻击者能同时修改文件和旁边的哈希文件，两者仍会匹配。真实流水线还需要可信的构建来源、受保护的产物存储及适当的签名或证明机制；示例只检验完整性，不宣称实现供应链认证。

将发布拆成准备、切换和确认

一个可审查的发布过程可以有三个阶段：

  1. 准备版本目录，核对产物和配置，不触碰当前版本。
  2. 在串行发布边界内切换 current 指针，记录上一个目标。
  3. 检查新版本的入口、关键资源和最小业务路径，失败则恢复指针。

对于 POSIX 上的静态文件模型，示例创建一个临时符号链接，再用同目录的替换操作切换 current：

temporary = root / (".next-" + uuid.uuid4().hex)
temporary.symlink_to("releases/" + version)
os.replace(str(temporary), str(root / "current"))

Python 对 os.replace 的约定包含同文件系统上的替换行为；跨文件系统操作可能失败。这个局部原子性不等于所有客户端同时切换，也不意味着断电后状态一定符合预期。已经打开文件的请求、CDN 缓存以及多个实例仍需要分别考虑。os.replace 文档

发布锁和版本检查解决不同的冲突

两个任务同时发布时，只把 symlink 替换做成原子操作仍然不够。较早的任务可能在较晚任务成功后执行“回退”，覆盖新的正确状态。

示例用 POSIX 文件锁包住切换和冒烟检查，要求所有发布者遵守同一锁协议；同时校验调用者认知中的 previous 与实际目标一致。锁限制同时执行，previous 检查拒绝基于过期状态的意图。

previous = os.readlink(str(current)) if current.is_symlink() else None
if previous != expected_previous:
    raise RuntimeError("stale deployment intent")
replace_pointer(root, "releases/" + version)
try:
    if not smoke(current):
        raise RuntimeError("smoke check failed")
except BaseException:
    replace_pointer(root, previous)
    raise

片段省略了首次发布无 previous 的分支；完整程序在这种情况下移除本次失败的指针。生产脚本还要限制冒烟检查时间、确认回退动作本身成功，并保护版本目录不被其他进程修改。文件锁是协作约定，不会阻止一个不遵守锁的外部部署器。

冒烟检查应该跨过最关键的边界

只检查首页返回 200，可能无法发现 JavaScript 和样式路径错误。静态站点至少应该读取一个入口页面和它引用的关键资源；带后端的应用则需要验证 API 契约及必要依赖。

但冒烟检查也不应该随意制造真实订单或发送消息。可以使用明确隔离的测试主体，或只读、可恢复的验证路径。检查要有可重复输入、清楚的成功标准和清理方式，不能把一个有副作用的“健康检查”高频运行在真实客户数据上。

版本切换后还应回读当前版本标识，避免检查请求命中了缓存或旧实例。多实例发布需要考虑混合版本窗口：新旧 API、资源和数据库结构必须在过渡期相互兼容，或者采用明确的流量隔离方式。

应用回退不等于数据回退

恢复旧二进制或静态目录通常比较直接，撤销数据库结构和已经发生的外部动作则复杂得多。若新版先删除了旧字段，再试图恢复旧应用，回退可能根本无法工作。

较稳妥的迁移常先扩展兼容结构，再逐步转换读写，最后在验证完成后收缩旧结构。每一阶段都要写清楚哪些版本能同时运行。需要回滚数据时，应有单独验证过的备份、恢复和一致性方案，不能把删除迁移脚本视为简单的 inverse 操作。

这也影响发布门槛：不可逆的数据操作，应在执行前有明确审批和恢复判断，而不是等冒烟失败后才发现“没有上一个状态可以恢复”。

CI权限不能为了方便而默认放大

部署需要的凭据与读取源代码需要的权限不同。可以把构建与部署拆成不同任务，用部署环境限制分支、审批及秘密访问；不可信来源的构建结果也不能直接获得生产权限。GitHub 部署环境

当前部署方案可以研究 OIDC 短期凭据，但云端仍须校验仓库、分支或环境等信任条件，不能因为令牌寿命短就接受所有来源。这里引用的是现行加固文档，不是声称 2021 年的系统已经采用全部当前设置。GitHub OIDC 指南

验证记录要能指出没有测什么

配套 Python 3.9.6 模型在 macOS 临时目录中通过五项测试：成功切换到准确产物、冒烟失败恢复旧版本、产物被修改时拒绝激活、过期发布意图被拒绝、既有版本目录不被覆盖。

python3 -m unittest -v

它没有验证远程上传、真实反向代理、多实例流量、断电持久性或数据库恢复，也没有执行 GitHub Actions。实际上线需要补齐这些目标环境检查。一个有价值的交付记录，应该同时包含已通过的范围和仍需验证的边界。
