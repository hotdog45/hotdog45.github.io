Go服务如何停止：context取消、goroutine退出与资源归还

以一个有界并发处理器为例，拆开取消通知、阻塞点退出和完成等待，建立可以验证的资源生命周期。

xq.Xiaofeng Qiao发布于 2026年10月23日本文暂时仅提供中文版本。

请求结束，工作为什么还在继续

设想一个报表接口：它把一批条目分给几个 worker，逐个查询依赖，再将结果汇总。调用方关闭页面后，HTTP 请求已经取消，但进程的连接数没有下降。继续增加并发，只会让问题更难复现。

这类问题的起点通常不是缺少 context.Context，而是生命周期没有闭合：有人发出停止通知，却没有人保证生产者、发送者和依赖调用都能退出。

本文从 2020 年 Go 1.15 的能力基线回看这个问题。配套代码只用当时已有的标准库 API，实际在 2026 年使用本机 Go 1.23.3 验证；这是一份在 2026 年整理的工程分析示例。现代的 WithCancelCause 不在示例中，它到 Go 1.20 才加入。Go 版本说明与context API 文档可以用于核对这个边界。

先为每一种资源找到归还者

“请求函数返回”不能自动证明它启动的工作都已完成。对这个处理器，先写下四个不变量：

  1. 任一条目失败后，不再把部分结果包装为完整报表。
  2. 上游取消后，任务分发和结果发送均有退出路径。
  3. 函数返回前，自己启动的生产者与 worker 已经结束。
  4. 并发数有上限，不能为每个输入无限创建 goroutine。

其中第三点最容易遗漏。cancel() 负责通知，等待需要另外安排。官方 context 文档也明确区分了取消通知和工作停止。context 取消约定

对象 谁创建 谁结束或归还
派生 context 处理器 处理器在所有返回路径调用 cancel
jobs channel 处理器 唯一生产者结束后关闭
results channel 处理器 全部发送者结束后，由协调者关闭
worker 处理器 worker 自己退出，处理器等待
HTTP 响应体、游标 实际依赖函数 取得资源的依赖函数及时关闭

这个表还没有替代码证明安全，但能暴露缺口：如果某个资源的归还者是“应该会自动释放”，就需要进一步检查。

一个阻塞点，就需要一个停止出口

下面是配套 Map 处理器中 worker 的核心部分。work 接收同一个派生 context；结果发送也监听取消，而不是只在进入函数时检查一次。

for j := range jobs {
    if ctx.Err() != nil {
        return
    }
    value, err := work(ctx, j.value)
    select {
    case results <- result{j.index, value, err}:
    case <-ctx.Done():
        return
    }
    if err != nil {
        return
    }
}

这里的 ctx.Err() 会在检查时已取消的情况下直接退出，不能替代 work 内部的取消支持。检查与调用不是原子操作，取消也可能恰好发生在两者之间。若 work 调用了一个永不返回、也不观察 context 的第三方函数，外层 select 无法强制终止它。此时需要给底层连接配置超时、使用支持取消的客户端，或者把不可控工作隔离为受控进程。为了让接口“尽快返回”而丢下它，并没有解决资源问题。

生产者同样通过 select 发送任务，取消时返回，并用 defer close(jobs) 结束输入。不能让下游关闭 jobs 来表达取消：生产者可能仍在发送，从而触发向已关闭 channel 发送的 panic。

还要避免一个更隐蔽的假设：select 不会赋予取消分支固定优先级。当发送和取消都已就绪时，发送仍可能被选择。因此，“调用 cancel 后一个结果也不再出现”不是这份接口的保证。它保证的是取消能够传播、所有自有工作可退出、最终返回准确的失败状态。若业务要求某个时点之后绝不产生写入，需要在实际写入方另行实施版本检查或状态约束，不能让 context 承担一个跨组件的原子事务承诺。

关闭 channel 和等待，必须有明确顺序

多个 worker 共同发送结果，任何一个 worker 都不拥有 results 的关闭权。示例用同一个 WaitGroup 跟踪生产者与所有 worker，在它们全部退出后关闭结果通道：

go func() {
    group.Wait()
    close(results)
}()

output := make([]int, len(values))
var firstErr error
for r := range results {
    if r.err != nil && firstErr == nil {
        firstErr = r.err
        cancel()
    }
    output[r.index] = r.value
}
if firstErr != nil {
    return nil, firstErr
}
if err := parent.Err(); err != nil {
    return nil, err
}
return output, nil

汇总方收到第一个错误后取消剩余工作，但继续等待 results 关闭。这样既能传播错误，也能确认这次调用拥有的工作已经收尾。成功结果按输入序号写入数组，不依赖 worker 完成顺序。

这份实现选择“任一失败，整体失败”。如果业务允许部分成功，返回类型应显式包含每项状态及完整度，不能只保留成功项，再以 nil 错误掩盖缺失。是否保留部分结果是业务约定，不是并发工具替团队做的决定。

为什么扩大缓冲区常常只是推迟问题

把 results 缓冲区从 1 改成 100，可能让小样本不再挂住。它成立的前提却是：未被消费的结果永远不超过 100。输入一变大，或者调用方更早退出，阻塞就会回来。

Go 官方的流水线文章讨论了下游提前停止消费时的泄漏路径；它给出的关键提醒，是让上游能够收到停止信号，而不是依靠猜测缓冲容量。Pipelines and cancellation

缓冲区仍然有价值：它可以吸收短暂速度差，减少同步开销。但它不应承担“保证取消后退出”这个职责。为吞吐调节缓冲，为停止设计协议，这两个问题需要分别验证。

验证退出，不只验证算出来的值

正常路径的测试检查输入顺序和完整结果。错误路径则要求返回错误且结果为 nil。更关键的测试是让两个 worker 都进入可取消的阻塞操作，然后取消父 context：

atomic.AddInt32(&active, 1)
defer atomic.AddInt32(&active, -1)
started <- struct{}{}
<-ctx.Done()
return 0, ctx.Err()

测试等待两个 started 信号后才调用 cancel，避免用睡眠猜测调度时机；Map 返回时，active 必须已经回到零。测试的超时只作为防止挂死的上限，不作为性能基准。这比比较整个测试进程的 goroutine 总数更直接，因为测试运行器和其他测试也可能创建 goroutine。

配套还检查预先取消时不调用 work、非法并发数被拒绝。建议运行：

go test -race -count=30 ./...
go vet ./...

竞态检测能发现实际执行路径上的数据竞争，不能证明所有调度都安全；30 次重复也不是形式化证明。仍需结合关闭权和等待关系审查代码。示例没有接数据库或真实 HTTP 服务，因此连接关闭、驱动取消行为和进程退出信号需要在实际集成环境另外验证。

停止能力是接口的一部分

一个可靠的并发接口，除了输入和输出，还应约定：谁可以取消、哪些调用响应取消、谁关闭资源、返回时还有没有后台工作。把这些条件写进代码和测试，比“所有函数都传了 context”更接近真正的可控并发。

示例的使用边界也很清楚：适合一次请求内、有界、可取消的任务汇总；不适合把已经对外承诺必须完成的任务仅绑定到浏览器请求。后者应该有持久化任务状态和独立生命周期，另行处理恢复、重复执行及补偿。
