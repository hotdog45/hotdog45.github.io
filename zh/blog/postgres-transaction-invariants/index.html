订单一致性：PostgreSQL事务隔离与乐观并发控制

用最后一件库存的并发预留解释事务不变量、条件更新、请求去重与版本比较，并给出可复现的双会话 SQL 实验和验证边界。

xq.Xiaofeng Qiao发布于 2026年10月23日本文暂时仅提供中文版本。

最后一件库存，不能只检查最后的数字

库存还有一件，两个请求都读到一，再各自创建一条预留记录，最后都把库存写成零。数据库没有出现负数，但两张有效预留已经占用了同一件商品。只检查 available >= 0，甚至可能得到一个看起来“正确”的结果。

讨论一致性时，我更愿意先写不变量：有效预留不能超过可分配库存；同一业务请求不能重复扣减；预留记录与库存变化必须一起成功或一起失败。库存数字、订单状态与重试结果要放在同一个推理范围，不能各自都说“已经加事务了”。以下用独立构造的单商品预留示例分析这些边界。

本文以 2019 年 10 月发布的 PostgreSQL 12 文档为回顾基线。相关机制并非都在 12 首次出现；版本号用于固定讨论语义。12 目前已经停止支持，新部署应选仍受支持的版本，并重新运行实验，而不是为了复盘安装旧生产版本。PostgreSQL 12 发布记录

事务保证原子性，不替你修正判断条件

下面的结构仍然有问题，即使外面包了 BEGIN 和 COMMIT：

读取 available 得到 old
如果 old >= 1：
    插入预留
    将 available 写成 old - 1

应用把“过去读到的值”写回去，另一个事务的业务决策可能已经使用了同一份库存。解决这种单行扣减，通常不必先升级整个系统的隔离级别，而是把资格判断和修改合成一条语句：

UPDATE inventory
SET available = available - 1, version = version + 1
WHERE sku = 'demo-widget' AND available >= 1
RETURNING available, version;

返回一行才说明本次取得库存，返回零行应走拒绝或重新读取的分支。UPDATE 执行成功不等于业务条件成立；客户端若忽略受影响行数，仍可能创建没有库存支撑的订单。UPDATE 与 RETURNING

PostgreSQL 默认的 Read Committed 对每条普通查询建立快照。并发更新同一行时，后一个更新会等待；前一个提交后，更新条件会针对新的行版本重新判断。因此在这个特定例子里，第一个请求扣到零，第二个请求不能再通过 available >= 1。这依赖明确的单行条件，不能直接外推到复杂跨行规则。事务隔离说明

把重复请求也放入同一个事务

库存扣减安全以后，还要处理同一个请求重试。一个请求如果第一次已经成功，再次到来应返回既有预留，而不是因为库存归零被误判为新的失败。示例用 request_id 主键去重，数量与库存增加数据库约束：

CREATE SCHEMA blog_order_demo;
CREATE TABLE blog_order_demo.inventory (
  sku text PRIMARY KEY,
  available integer NOT NULL CHECK (available >= 0),
  version integer NOT NULL DEFAULT 0
);
CREATE TABLE blog_order_demo.reservations (
  request_id text PRIMARY KEY,
  sku text NOT NULL REFERENCES blog_order_demo.inventory(sku),
  quantity integer NOT NULL CHECK (quantity > 0)
);
INSERT INTO blog_order_demo.inventory(sku, available)
VALUES ('demo-widget', 1);

这里的约束是最后防线，不能替代业务检查。CHECK (available >= 0) 只看一行数据，无法发现前面“库存是零、却有两张预留”的错误；主键也必须声明在真实的业务作用域内。多租户系统通常需要把租户与业务请求号一起纳入唯一键。NOT NULL 则避免可空键带来的语义缺口。约束与唯一性

下面的函数展示完整的数据库内原子步骤。实际应用还应在调用之前完成鉴权、请求大小限制和业务字段校验：

CREATE FUNCTION blog_order_demo.reserve(
  p_request text, p_sku text, p_quantity integer
) RETURNS text LANGUAGE plpgsql AS $$
DECLARE
  inserted integer;
  previous blog_order_demo.reservations%ROWTYPE;
BEGIN
  IF p_request IS NULL OR p_request = ''
     OR p_quantity IS NULL OR p_quantity <= 0 THEN
    RAISE EXCEPTION 'invalid reservation request';
  END IF;
  INSERT INTO blog_order_demo.reservations(request_id, sku, quantity)
    VALUES (p_request, p_sku, p_quantity)
    ON CONFLICT (request_id) DO NOTHING;
  GET DIAGNOSTICS inserted = ROW_COUNT;
  IF inserted = 0 THEN
    SELECT * INTO STRICT previous FROM blog_order_demo.reservations
      WHERE request_id = p_request;
    IF previous.sku IS DISTINCT FROM p_sku
       OR previous.quantity <> p_quantity THEN
      RAISE EXCEPTION 'request_id reused with different input';
    END IF;
    RETURN 'replayed';
  END IF;
  UPDATE blog_order_demo.inventory
    SET available = available - p_quantity, version = version + 1
    WHERE sku = p_sku AND available >= p_quantity;
  IF NOT FOUND THEN
    RAISE EXCEPTION 'insufficient stock';
  END IF;
  RETURN 'created';
END;
$$;

函数先争取业务请求号，再扣库存。请求已存在时比较参数，不能把“同键异参”默默吞掉。库存不足则抛出错误，由事务回滚本次插入的预留。这里不能在异常后仍然提交其他业务步骤，也不应该把所有唯一冲突都当作成功；冲突可能来自不同约束。INSERT 与 ON CONFLICT

版本号适合“不能覆盖别人修改”的编辑

下单扣减表达的是“只要现在足够就扣一件”；后台编辑表达的可能是“只有我看到的那个版本没有变，才把库存设为五”。这两种意图不一样。后者可以用显式版本比较：

UPDATE blog_order_demo.inventory
SET available = 5, version = version + 1
WHERE sku = 'demo-widget' AND version = 0
RETURNING version;

零行意味着版本已经变化，界面应读回最新值，让操作者合并或重新确认。不断用同一个旧版本自动重试没有意义；把旧页面的绝对值覆盖成最新值，更是绕过了比较。还要保证所有相关写入路径都会递增版本，否则遗漏的后台脚本会破坏这份约定。

显式锁是另一个选项。需要先读一行再做若干判断时，SELECT ... FOR UPDATE 可以在事务内保护这行直到结束，但它会使竞争者等待；锁内调用慢速外部 API 会把网络延迟变成数据库排队。多行更新应统一锁顺序，缩短锁持有时间，而不是把长业务流程整个装进一个大事务。行锁与死锁

隔离级别升级后，重试边界也要升级

跨行规则，例如某个集合的总预留不能超出额度，未必能由一条行级谓词表达。可以重新设计数据，把额度集中到可原子更新的记录；也可以评估显式锁或 Serializable。选择应来自不变量和竞争模式，而不是把更高隔离级别当成不需要理解并发的开关。

遇到数据库的序列化失败，需要回滚并重新执行整个事务，包括产生决策的读取；只重跑最后一条 SQL 可能沿用已经失效的判断。重试也要有次数和截止时间，事务外的通知必须避免重复。序列化与重试边界 应用最好按 SQLSTATE 识别错误，区分 40001 序列化失败、40P01 死锁与业务拒绝，而不是匹配会随语言变化的错误文本。PostgreSQL 错误码

用两个会话验证等待与回滚

在一次性测试数据库执行建表与函数脚本后，按下面的顺序运行。不要在生产库创建此教学 schema。

-- 会话 A：先执行，但暂不提交
BEGIN;
SELECT blog_order_demo.reserve('request-a', 'demo-widget', 1);
-- 预期 created

-- 会话 B：A 未提交时执行；预期等待 A
BEGIN;
SELECT blog_order_demo.reserve('request-b', 'demo-widget', 1);

-- 回到 A
COMMIT;

-- B 预期得到 insufficient stock；随后执行
ROLLBACK;

最后查询应只有一张预留，库存零、版本一；再次使用 request-a 应得到 replayed 且不再扣库存。再做三组变体：A 回滚而非提交，两个会话使用相同请求号，以及相同请求号换数量。检查最终表数据，并记录哪个会话等待、哪个事务回滚，才能把接口结果和数据库状态对上。

上述 SQL 与双会话实验尚未连接 PostgreSQL 实际执行。随稿 examples/inventory_state_model.py 的六项纯状态模型测试已在 Python 3.9.6 通过，覆盖两种串行顺序、重复请求、异参冲突、失败回滚、旧版本拒绝，以及一个“库存不负但超卖”的反例。它验证业务推理，不模拟 PostgreSQL 的 MVCC、锁等待或 SQL 语法；不能用它替代目标数据库集成测试。

结论

订单一致性要从跨记录的不变量出发，再选择数据库能原子执行的条件。单行条件扣减、请求唯一约束和事务解决这一例子的核心问题；版本号保护的是另一种“基于旧视图编辑”的意图。隔离级别、锁和重试必须共同设计，最终用并发会话及提交后的数据证明结果，而不是仅凭“使用了事务”作保证。
