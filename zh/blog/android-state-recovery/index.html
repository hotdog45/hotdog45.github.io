Android页面重建：业务状态、界面状态与恢复顺序

从搜索列表的旋转与进程重建出发，区分可保存的小型界面状态、可重算数据和必须持久化的业务事实。

xq.Xiaofeng Qiao发布于 2026年10月23日本文暂时仅提供中文版本。

用户回来时，究竟希望恢复什么

一个搜索列表在旋转后回到顶部，通常不会被归类成崩溃，却足以让人怀疑刚才的操作是否成功。搜索词、筛选条件、正在阅读的位置和服务器返回的商品列表，看起来都属于“页面状态”，实际需要不同的保存方式。把它们一起塞进一个对象，页面重新创建时便很难判断哪些应该恢复，哪些应该重新加载。

本文在2026年回顾2015年前后以Activity、View和Bundle为主的实现方式，使用虚构搜索列表分析恢复契约。现代Android文档还讨论ViewModel、SavedStateHandle和Compose；这些是今天选择方案时的参考，不能回写成2015年的实现。验证程序采用Java 8语言基线，不依赖Android运行时。

先定义用户意图：系统重建同一个搜索页面时保留查询和阅读锚点；新的明确搜索入口应覆盖旧查询；用户结束页面后重新打开，不应自动复活一次已经结束的临时交互。Android官方文档区分了配置变化、系统进程回收与用户主动结束页面，也区分了内存状态、保存状态和持久化数据的寿命。状态保存指南

小型快照不是业务数据库

保存快照可以包含查询字符串、已选筛选ID、列表锚点ID和相对偏移。商品全集、位图、网络请求对象和Activity引用不适合放进去：它们要么体积较大，要么无法跨进程恢复，要么只是执行过程中的对象。重新加载列表时，服务器结果才是商品是否仍存在、是否有库存的依据。

购物草稿、用户主动编辑的长文本和待发送业务记录则是另一类问题。若用户退出应用仍期望它们存在，应该设计持久化保存、版本迁移和失败处理，不能依赖某次生命周期回调恰好被调用。把“UI暂存成功”当作“业务已提交”，会让恢复出来的界面看起来完整，服务端却没有相应记录。

对每个字段，可以问一个很具体的问题：丢失后是重新计算、重新请求，还是会丢掉用户无法重现的输入？前两类通常只存恢复所需的小标识；最后一类需要更可靠的持久化策略。恢复快照最好也有自己的schema，方便旧版本残留数据遇到新代码时采取可解释的降级。

恢复有顺序，不能只在最后调用一次setText

搜索词应该在发起加载之前恢复，否则页面可能先发出默认查询，之后才把输入框改成旧查询。界面与结果因此属于两套条件。列表位置也不能在数据尚未到达时恢复：以前的第八行，未必还是本次结果的第八行。更稳妥的做法是保存稳定条目ID，等对应查询的数据到达后再寻找锚点；条目已删除时使用明确的回退位置。

另外，新的外部入口需要自己的优先级。例如用户从快捷入口明确搜索“laptop”，旧快照里的“camera”不应抢回控制权。空字符串也可能是用户明确要求清空查询，不能和“没有提供新查询”混为一谈。

下面的完整程序用字符串Map模拟小型保存容器，便于在桌面环境验证决策。接入Activity时，应把这些少量字段映射到Bundle，并按实际页面生命周期调用；Map测试不等于已经验证Bundle序列化、View自动保存或设备进程重建。

import java.util.Arrays;
import java.util.HashMap;
import java.util.List;
import java.util.Map;

public final class AndroidStateRecovery {
    static final class SearchState {
        final String query;
        final String anchorId;
        final int offset;

        SearchState(String query, String anchorId, int offset) {
            this.query = query;
            this.anchorId = anchorId;
            this.offset = offset;
        }

        Map<String, String> save() {
            Map<String, String> snapshot = new HashMap<>();
            snapshot.put("schema", "1");
            snapshot.put("query", query);
            snapshot.put("anchor", anchorId);
            snapshot.put("offset", Integer.toString(offset));
            return snapshot;
        }

        static SearchState restore(Map<String, String> snapshot, String newRouteQuery) {
            if (newRouteQuery != null) return fresh(newRouteQuery);
            if (snapshot == null || !"1".equals(snapshot.get("schema"))) return fresh("");
            String query = snapshot.get("query");
            String anchor = snapshot.get("anchor");
            if (query == null || query.length() > 200 || anchor == null) return fresh("");
            try {
                int offset = Integer.parseInt(snapshot.get("offset"));
                if (offset < 0 || offset > 10000) return fresh("");
                return new SearchState(query, anchor, offset);
            } catch (NumberFormatException invalid) {
                return fresh("");
            }
        }

        static SearchState fresh(String query) { return new SearchState(query, "", 0); }

        int anchorIndexAfterLoad(List<String> itemIds) {
            int index = itemIds.indexOf(anchorId);
            return index < 0 ? 0 : index;
        }
    }

    static void check(boolean condition, String label) {
        if (!condition) throw new AssertionError(label);
    }

    public static void main(String[] args) {
        SearchState original = new SearchState("camera", "item-9", 120);
        Map<String, String> snapshot = original.save();
        SearchState restored = SearchState.restore(snapshot, null);
        check(restored.query.equals("camera"), "query restored before reload");
        check(restored.offset == 120, "small viewport offset retained");
        check(restored.anchorIndexAfterLoad(Arrays.asList("item-8", "item-9")) == 1,
                "anchor located after data arrives");
        check(restored.anchorIndexAfterLoad(Arrays.asList("item-8")) == 0,
                "removed anchor falls back");
        SearchState redirected = SearchState.restore(snapshot, "laptop");
        check(redirected.query.equals("laptop") && redirected.anchorId.isEmpty(),
                "explicit new route overrides prior snapshot");
        check(SearchState.restore(snapshot, "").query.isEmpty(), "explicit clear is not missing");
        Map<String, String> unknown = new HashMap<>(snapshot);
        unknown.put("schema", "2");
        check(SearchState.restore(unknown, null).query.isEmpty(), "unknown snapshot rejected");
        Map<String, String> corrupt = new HashMap<>(snapshot);
        corrupt.put("offset", "not-a-number");
        check(SearchState.restore(corrupt, null).offset == 0, "corrupt offset handled");
        check(SearchState.restore(null, null).query.isEmpty(), "fresh start independent of snapshot");
        check(!snapshot.containsKey("items") && !snapshot.containsKey("loading"),
                "derived state excluded");
        System.out.println("PASS: 10 state-recovery contract assertions; no Android runtime");
    }
}

这里没有保存 loading，因为重建前的请求对象已经不能作为当前请求状态的依据。恢复查询后重新进入加载状态，比恢复一个永远等不到旧回调的“加载中”更可控。错误提示也要区分：旧网络失败可以保留为诊断历史，但新页面是否继续显示它，应由当前恢复流程决定。

Activity和View各自承担什么

使用传统View体系时，具有稳定ID的View可能参与框架自动状态保存；应用仍需要正确调用父类的状态保存逻辑，并处理自己额外拥有的字段。恢复代码还要避免和框架的自动恢复互相覆盖。不能一边让View恢复旧输入，一边又在稍后的通用初始化里把它重置成默认值。Activity生命周期说明

一个可审查的接入顺序是：建立页面依赖，决定本次入口与快照的优先级，构造恢复后的查询状态，渲染输入，再加载数据，最后按稳定ID恢复锚点。UI事件绑定也需要避免把程序恢复动作当成一次新的用户输入，导致重复请求或重新清空锚点。

这条顺序还需要一次“恢复完成”的明确边界。例如列表先收到缓存、再收到网络结果，不能每批数据到达都强行滚回旧锚点，否则用户已经开始新的滚动，页面又突然跳走。可以把锚点恢复作为本次重建的一次性效果；用户发生新的主动滚动后，就放弃尚未执行的旧锚点。代码模型只负责找到位置，实际接入时要把这项效果与用户事件的优先级一起验证。

将所有状态放进静态变量，看起来能躲过旋转，但进程结束后同样丢失，还可能把某个Activity或大对象留在内存里。强行忽略配置变化也只是改变重建路径，不等于已经解决语言、字体、窗口大小等配置更新。现代ViewModel可以简化部分内存生命周期管理，但它本身不是跨系统进程回收的持久化方案。

测试恢复，而不只是测试旋转

本例编译为Java 8兼容字节码，在Corretto 11.0.23运行，十组断言通过：查询、偏移、数据到达后的锚点、锚点删除、新入口覆盖、明确清空、未知schema、损坏字段、全新启动，以及派生数据不进入快照。

javac --release 8 -d classes AndroidStateRecovery.java
java -cp classes AndroidStateRecovery

真实Android验证还需要区分不同动作。旋转主要覆盖Activity重建；“不保留活动”不能完整代表进程死亡；强制停止又带有用户主动结束的语义。应分别记录配置重建、应用在后台被系统回收后返回、用户主动退出再进入，以及新深链覆盖旧页面的结果。验证时还要包含数据已变化、离线和草稿保存失败，而不是只看同一列表能否滚回原处。

恢复测试也应检查请求次数和副作用次数。界面文本正确，却重复订阅同一个数据源、重新发送一次业务提交，仍然属于恢复错误。加载查询可以根据缓存策略重复进行，提交订单则需要独立的幂等与状态核对，不能仅凭恢复后按钮仍显示“处理中”就再次执行。

好的状态恢复不是把旧屏幕逐像素复活，而是把用户意图和当前真实数据重新对齐。先划分字段的寿命，再决定恢复优先级与加载顺序，通常比不断增加生命周期回调里的补丁更容易维护。
