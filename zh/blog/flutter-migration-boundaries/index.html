Flutter初次迁移：先定义原生边界，再移动业务流程

以订单详情的渐进迁移为例，拆开导航、会话与副作用归属，给跨端消息定义可测试的协议和回退条件。

xq.Xiaofeng Qiao发布于 2026年10月23日本文暂时仅提供中文版本。

从一个订单详情页开始，为什么仍会牵动整个应用

“先迁移一个页面”听起来是很小的任务。真正开始后，却可能发现它依赖登录会话、原生导航、图片缓存、埋点、分享、支付和通知跳转。页面数量不是迁移工作量的可靠单位，一条能进入、操作、退出并恢复的业务流程，才更接近可验收的边界。

本文以虚构的订单详情流程作为渐进迁移的分析示例。回顾年份选2018，是因为Flutter 1.0在该年发布；官方当年的回顾已经提到Add to App及仍在演进的平台能力。架构分析在2026年重新整理，当前文档和Dart验证程序用于说明今天可以怎样验证这些边界。2018年官方发布回顾

一个合理的首批目标可以是：原生列表打开Flutter订单详情，详情读取模拟订单，用户返回原生列表；登录失效时显示明确状态，重复点击不多开页面，关闭迁移开关后还能进入原有详情。先不迁移支付、消息推送和完整登录体系，并不是忽略它们，而是让副作用继续由现有系统承担，减少第一阶段的同时变化。

业务所有权比目录结构更值得先讨论

把Dart文件放进 features/orders 不会自动得到清晰边界。需要先画出谁是事实来源：宿主拥有导航栈和会话生命周期；Flutter拥有详情页的加载、空、失败与展示状态；服务端仍负责订单权限与最终业务状态。订单ID可以跨边界传递，长期访问令牌、支付结果的权威判定和原生对象引用不应随意传递。

另一个选择是把网络、登录和缓存也迁入Dart。新项目可能因此更一致，但对渐进迁移来说，两套会话刷新和缓存失效策略容易产生互相看不见的状态。反过来，让每一次页面内部操作都经由原生转发，也会把Flutter变成一个充满通道调用的展示壳。取舍应依据需要共享的生命周期和可独立验证的业务能力，而不是依据“跨端代码比例越高越好”。

当前Flutter官方文档说明了按模块集成到已有应用的方式；今天支持的引擎管理、平台范围和集成工具，比2018更完整。它适合用来决定当前实施方案，不能直接当作历史版本安装手册。当前Add-to-app文档

把一次跨端调用写成一个小协议

假设宿主提供 openOrder 命令。与其直接发送一个字符串，可以定义版本、请求ID、会话修订号和payload。版本解决协议是否兼容，请求ID解决同一次操作是否重放，会话修订号解决退出登录之后的旧消息是否仍有效。三者不能互相替代；新请求不意味着新会话，同一会话里也有多个业务操作。

{
  "version": 1,
  "requestId": "r1",
  "method": "openOrder",
  "sessionRevision": 7,
  "payload": {"orderId": "demo-42"}
}

原生端和Dart端都应校验必要字段。不能因为消息来自应用自己的Flutter模块，就默认它的参数一定正确。未知方法返回明确错误，协议版本不匹配时停止该调用；不要悄悄把未知字段或错误类型转换成可执行命令。对外部深链输入，还应单独验证来源和参数。会话修订号是本地失效机制，不是安全凭据；服务端必须继续核实当前用户是否有权访问订单。

当前Platform Channel使用异步消息，并支持一组可序列化的数据类型。通道只提供传递机制，业务仍需定义错误、超时和版本约定；线程要求也要按平台API处理。当前官方通道说明

先用无引擎模型验证拒绝条件

下面是完整的纯Dart协议模型，针对当前Dart 3.6.0执行，不是Flutter 1.0宿主代码。它没有调用原生页面，没有联网，也没有完成订单；opened只记录模型批准执行的次数，accepted只表示协议检查通过。

import 'dart:convert';

// Current Dart validation model, not a Flutter 1.0 host implementation.
class RouteGate {
  int sessionRevision = 7;
  final Map<String, String> accepted = <String, String>{};
  int opened = 0;

  Map<String, dynamic> handle(Map<String, dynamic> message) {
    final dynamic version = message['version'];
    if (version is! int || version != 1) return result('unsupported_version');
    final dynamic id = message['requestId'];
    final dynamic revision = message['sessionRevision'];
    final dynamic payload = message['payload'];
    if (id is! String || id.isEmpty || revision is! int || payload is! Map) {
      return result('invalid_request');
    }
    if (message['method'] != 'openOrder') return result('unknown_method');
    if (revision != sessionRevision) return result('stale_session');
    final dynamic orderId = payload['orderId'];
    if (orderId is! String || !RegExp(r'^demo-[0-9]+$').hasMatch(orderId)) {
      return result('invalid_order_id');
    }
    final String key = '$revision:$id';
    if (accepted.containsKey(key)) {
      return result(accepted[key] == orderId ? 'duplicate' : 'id_conflict');
    }
    accepted[key] = orderId;
    opened += 1;
    return result('accepted');
  }

  void logout() {
    sessionRevision += 1;
    accepted.clear();
  }

  Map<String, dynamic> result(String status) => <String, dynamic>{'status': status};
}

Map<String, dynamic> request(String id, String order, {int revision = 7}) =>
    <String, dynamic>{
      'version': 1,
      'requestId': id,
      'method': 'openOrder',
      'sessionRevision': revision,
      'payload': <String, dynamic>{'orderId': order},
    };

void expectStatus(RouteGate gate, Map<String, dynamic> message, String expected) {
  final String actual = gate.handle(message)['status'] as String;
  if (actual != expected) throw StateError('$actual != $expected');
}

void main() {
  final RouteGate gate = RouteGate();
  expectStatus(gate, request('r1', 'demo-42'), 'accepted');
  expectStatus(gate, request('r1', 'demo-42'), 'duplicate');
  expectStatus(gate, request('r1', 'demo-99'), 'id_conflict');
  expectStatus(gate, request('r2', 'not-an-order'), 'invalid_order_id');
  final Map<String, dynamic> wrongMethod = request('r2', 'demo-42');
  wrongMethod['method'] = 'deleteAccount';
  expectStatus(gate, wrongMethod, 'unknown_method');
  final Map<String, dynamic> wrongVersion = request('r2', 'demo-42');
  wrongVersion['version'] = 2;
  expectStatus(gate, wrongVersion, 'unsupported_version');
  final Map<String, dynamic> decimalVersion = request('r2', 'demo-42');
  decimalVersion['version'] = 1.0;
  expectStatus(gate, decimalVersion, 'unsupported_version');
  final Map<String, dynamic> malformed = request('r2', 'demo-42');
  malformed['payload'] = 'wrong shape';
  expectStatus(gate, malformed, 'invalid_request');
  gate.logout();
  expectStatus(gate, request('r3', 'demo-42'), 'stale_session');
  expectStatus(gate, request('r3', 'demo-42', revision: 8), 'accepted');
  if (gate.opened != 2) throw StateError('unexpected side effect count');
  print(jsonEncode(<String, dynamic>{
    'passed': 10,
    'opened': gate.opened,
    'scope': 'pure Dart protocol model; no Flutter engine or device',
  }));
}

同一个请求ID携带不同订单时，返回 id_conflict，比一律当重复成功更安全。否则调用方复用了ID，却收到了另一个业务操作的成功回执，排查时很难知道哪个请求真正执行过。去重表在示例中仅驻留内存，并在登出时清空；生产实现还要定义保存期限、容量和多引擎是否共享。对于扣款、提交订单等服务端副作用，必须在服务端另做幂等，不能把内存表当作“恰好一次”的证明。

这段程序并不负责跨线程同步。真实宿主应在约定执行上下文中串行处理导航决策，异步工作完成后重新检查会话是否仍有效。引擎重启或进程被回收后，不能依赖旧内存里保留了请求ID。

回退开关要放在进入流程的位置

首批迁移最容易遗漏的，是成功进入Flutter后才发现无法安全退出。开关最好由宿主在进入详情流程之前决定本次使用旧页还是新页，同一次流程保持路由一致。若新旧页面随时互相抢入口，导航栈与回调会更难解释。

缓存和本地数据库也需要兼容计划。只切回旧页面但旧代码读不了新写的数据，不叫完整回退。涉及数据结构变化时，先确定双读、迁移或不可逆步骤；若无法安全回滚，就应把那一步从首批迁移中移出，或把恢复方案单独评审。回退决策也不能仅依据崩溃率，登录失败、重复导航、页面空白和业务状态不一致同样可能阻断使用。

验收包含协议、界面和宿主三层

模型可在当前Dart环境运行 dart analyze flutter_boundary_contract.dart 和 dart run flutter_boundary_contract.dart。本次静态分析无问题，十组状态断言通过，模型中的两次合法进入只产生两次计数。测试覆盖协议版本的值与整数类型、方法、payload形状、订单ID、重放冲突和退出登录后的旧消息，不依赖真实等待或网络快慢。

下一层用Widget测试验证加载、失败、重试及返回状态；再以集成测试把原生入口、Flutter详情、返回宿主、前后台切换和深链唤起串起来。Flutter官方集成测试文档提供了运行到模拟器或设备的路径，本次只验证纯Dart模型，没有运行这些设备测试。集成测试说明

迁移完成的证据应该能回答：旧入口是否仍可用，错误是否可解释，会话失效后是否拒绝旧动作，重复触发是否产生多次副作用。把这些问题先写成协议和验收条件，再逐步迁移模块，比先追求所有页面统一使用同一个框架，更容易控制范围和交付风险。
