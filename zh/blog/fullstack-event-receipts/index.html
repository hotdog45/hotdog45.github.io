React、Go与脚本协同：从事件接收到幂等回执

以自主交互工作台 Demo 为例，核对界面状态、Go 事件接收与 Node 批处理的同一条证据链。

xq.Xiaofeng Qiao发布于 2026年10月23日本文暂时仅提供中文版本。

三种语言要描述同一次操作

一个作品页面可以同时展示聊天、直播控制台与自动化流水线，但技术标签不会自动形成完整系统。最值得验证的是：用户点一次按钮，界面显示的结果是否来自实际服务；同一组输入再执行，脚本与页面能否解释不同的回执。

本文复盘自主创作的交互工作台场景 Demo，使用模拟数据。依据是 2026 年 10 月 23 日读取的站内 demos/ui/scene.jsx、Go 服务和 Node 脚本快照。公开源码现位于 interaction-workbench，旧仓库地址会重定向；公开仓库的目录正在演进，本文以随文保存的文件摘要为复核基准，不声称这些路径与最新提交完全一致。

React 管交互，业务结果来自 Go

页面先访问健康接口，确认响应的 backend 为 Go，再显示“本机联调”；连接不可用时使用浏览器夹具，并显示“浏览器演示”。两种模式都能演示流程，但只有前者经过服务端。本次审查还发现健康探测只发生在组件挂载时，运行中切换后端不会自动重新探测；产品化时应增加明确的连接状态与重试入口。

自动化界面有 processed、filtered、replayed、failed 四种行状态。点击后清空旧结果，禁用运行按钮，逐条处理固定样例，最后展示汇总。关键区别是：filtered 表示同一输入批次内的重复行没发到后端；replayed 表示请求确实发出，后端认出已有事件。

当前汇总中的“处理成功”同时包含新建和重放，不能解读为新增业务效果数。若继续扩展，应从行结果派生新建、重放、失败统计，减少多处维护计数造成的矛盾。React 官方关于状态结构的建议，同样适用于这类多阶段界面。React 状态结构

一份夹具，两个入口

React 与 Node 都读取同一份 fixtures.json。五条模拟事件中，一条重复，另有一条首次请求返回模拟瞬时失败。Node 的 planEvents 不仅过滤相同 ID，还比较事件类型、载荷和失败标记；同 ID 内容变化会在发送前报错。页面目前只对受控夹具按 ID 去重，不能据此宣称具备任意上传文件的冲突校验能力。

{"id":"demo-103","kind":"asset.observed","payload":"sample-chain-event","simulateFailure":true}

这条记录的名字带有链上场景，但载荷只是字符串，不读取钱包或区块链。类似地，聊天答案来自固定知识与角色文本，人工接管是界面标志；直播区域验证房间状态转换，不发送音视频。划清这些边界，评审者才能判断哪些集成已经可运行、哪些服务需要另外接入。

Node 默认只输出规划，显式执行才发请求。runBatch 将目的地限制为指定本机 HTTP 地址、端口与路径，并拒绝用户名、查询参数和片段。这个限制是本脚本的固定用途约束，不是通用网络沙箱，也不等于后端有身份认证。

回执让首跑与重放可观察

Go 在互斥锁内检查事件表。新事件成功后返回 201，包含 ID、duplicate:false 和尝试次数；已有相同内容返回 200 与 duplicate:true；同 ID 内容改变返回 409。模拟 503 发生在首次写入事件表之前，因此客户端保留原 ID 重试会得到正常的新建结果。

if old, ok := s.events[in.ID]; ok {
    if old != in {
        fail(w, 409, "event_id_conflict")
        return
    }
    jsonResponse(w, 200, map[string]any{"id": in.ID, "duplicate": true})
    return
}

关联 ID 也用于逐行检查：请求中的 demo-103 必须对应同一个回执 ID，不能只统计四个成功响应。当前 Node 实现直接接受服务端 JSON，测试核对了结果 ID；生产客户端还需要运行时响应结构和 ID 校验，不能把这项测试断言误认为运行时防御。

Node 只对明确的 503 在三次尝试预算内重试，单次请求设三秒取消信号；网络异常、超时和其他失败状态会抛出，当前没有指数退避。fetch、AbortSignal.timeout 的行为与版本依据见 Node 20.19.4 官方文档。取消等待也不能证明服务端没有处理请求，需要保留同一事件身份继续核对。

入口相同，失败策略仍要单独约定

源码还暴露了一个容易忽略的差异：页面把失败写成一行日志，然后继续后续事件；CLI 遇到无法恢复的错误会抛出，后续事件不再发送。因此，两者共享夹具与接口，却不是相同的批次调度器。命令行退出失败时，前面已成功的事件仍然存在，不能把退出码理解成整批回滚。

对于交互演示，继续执行有利于同时观察多种结果；对于部署脚本，尽早失败可能更合适。若以后要求页面与脚本严格一致，可以把计划与结果归并提炼成共享纯函数，把网络适配保留在各自入口。当前不为了凑同构架构搬动代码，而是先把差异写成验收条件。页面按钮禁用只限制当前组件的重复点击；另一标签页或 CLI 同时提交，仍需 Go 的事件身份判定，不能由前端 busy 代替。

用隔离真 HTTP 测试连接契约

为避免碰到原 Demo 的共享端口，验证复制七个源文件到独立目录，记录 SHA-256。新增 Go 测试创建全新的 Service，用 httptest 在随机回环端口启动真实 Handler；Node 测试适配器把原客户端校验通过的固定地址映射到该端口。它保留实际请求、HTTP 状态和 JSON 处理，但不验证原站代理与固定端口配置。Go httptest 文档

实际使用 Node 20.19.4、Go 1.23.3，开启 race 检测。首次运行得到：

观察项 首次 同服务内第二次
输入 / 唯一事件 / 本批过滤 5 / 4 / 1 5 / 4 / 1
503 后重试次数 1 0
新建回执 4 0
重放回执 0 4

demo-103 首次轨迹为 503、201，回执尝试次数为 2；第二批四条全部为 200。另有同 ID 改载荷得到 409、外部地址在调用 fetch 前被拒绝的负例。完整轨迹保存在 bridge-evidence.json，不是手工填写的展示数字。

随文 examples/fullstack-contract/README.md 给出运行方法。6 个 Go 测试函数通过，包括原有聊天流、房间状态、并发重复提交、来源与请求体校验，以及新增跨语言集成和重建边界。CLI 的规划检查与默认 dry-run 也分别通过。

把证据范围交代清楚

本次新增验证覆盖 Node 到 Go 的真实本地 HTTP，不包含浏览器点击、移动端布局或整站构建；React 部分依据源码审查。页面演示与端到端浏览器验收应分开报告，不能用服务测试替代截图和交互回归。

事件、尝试次数、房间版本与回执目前都在进程内存。新增测试重新构造 Service 后，同事件再次得到 201，明确证明没有跨重启持久化。后端的本地 Origin 检查也不是完整认证体系。若接真实业务，需要在持久化、权限、响应校验和运行观测上补齐契约。

这个 Demo 最有价值的成果，是能把同一组模拟输入贯穿到界面语义、脚本计划、服务判定与可重放证据。评审者可以运行它、检查首跑与重放的差异，并清楚知道下一阶段要接入哪些真实能力。
