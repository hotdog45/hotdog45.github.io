iOS异步回调与对象生命周期：从引用环到取消边界

把对象是否存活、请求是否有效和界面是否仍需要结果拆开处理，用可复现的Objective-C程序验证晚到回调。

xq.Xiaofeng Qiao发布于 2026年10月23日本文暂时仅提供中文版本。

页面已经离开，请求为什么还在影响界面

列表搜索是一个很小的功能，却把异步代码的三个问题放在同一处：页面退出后能否释放，旧请求返回后能否覆盖新结果，用户点击取消后还有没有代码继续运行。只在回调里添加一行 weakSelf，通常只能回答第一个问题。

这篇文章以2015年前后的Objective-C、ARC与Block写法为回顾对象，在2026年重新梳理现在仍常见的生命周期边界。验证使用当前macOS上的Foundation和Clang，不包含UIKit或设备网络栈；代码采用ARC和Block这一时期已有的表达方式。

先把目标写成可观察的规则：页面所有者释放后不能因回调被强行留住；只接受当前请求的结果；取消会使当前结果失效；请求成功、失败、取消最终都必须有清理路径。最后一条不是“立即释放所有资源”的保证，而是需要代码明确说明谁负责收尾。

引用关系和业务有效性是两张不同的图

考虑 页面 → 请求对象 → completion Block → 页面。前三段都是强引用，最后一段若捕获 self，就可能形成引用环。Apple的Objective-C文档解释了Block捕获对象的强引用，以及弱引用打断这一关系的方式。官方Block说明

但是，弱引用回答的是“对象还在吗”，不是“这条结果还有资格修改它吗”。用户先搜A再搜B，页面始终活着；A晚于B返回时，弱引用不会阻止A覆盖B。另一个场景是用户取消操作后仍留在页面，弱引用同样非空。

因此需要两个独立条件：回调执行期间取得一个临时强引用，确保这一段使用过程中对象不消失；再比较请求代次，确认结果仍属于当前意图。临时强引用只在回调执行期间存在，和长期把所有者捕获进Block不同。若数据本来由应用级仓库负责完成，生命周期也不必绑定页面；这时应由仓库接收结果，页面仅订阅自己的可见状态，不能机械地把所有回调都改成弱引用。

先约束线程，再引入代次

下面的最小程序把所有方法调用和结果接收限制在同一串行执行上下文。真实UIKit接入可以把这些状态操作统一放到主线程，但不应把耗时解析也塞进主线程。若服务库在任意队列回调，先切到约定队列，再读取或修改代次；单纯把属性声明成 atomic，不能让“比较代次并写入结果”变成一个原子业务操作。

FakeTask故意允许取消之后仍递交完成结果，用来测试最不利的时序。它不是对NSURLSession或所有第三方SDK的精确模拟。具体API是否回调、在哪个队列回调，要查各自契约。Apple对Operation的取消也要求任务实现配合处理，不能把取消请求理解成任意执行中的工作已被强行终止。Operation文档

#import <Foundation/Foundation.h>

@interface FakeTask : NSObject
@property(nonatomic, copy) void (^completion)(NSString *);
@property(nonatomic) BOOL cancelled;
@property(nonatomic) BOOL completesOnCancel;
- (void)cancel;
- (void)deliver:(NSString *)value;
@end

@implementation FakeTask
- (void)cancel {
    self.cancelled = YES;
    if (self.completesOnCancel) [self deliver:@"cancel-synchronously"];
}
- (void)deliver:(NSString *)value {
    // Deliberately allow a late completion after cancel in this test double.
    void (^completion)(NSString *) = self.completion;
    self.completion = nil;
    if (completion) completion(value);
}
@end

@interface RequestOwner : NSObject
@property(nonatomic, strong) FakeTask *task;
@property(nonatomic, copy) NSString *value;
@property(nonatomic) NSUInteger generation;
@property(nonatomic) NSUInteger updates;
- (FakeTask *)start;
- (void)cancelCurrent;
@end

@implementation RequestOwner
- (FakeTask *)start {
    NSUInteger ticket = ++self.generation;
    [self.task cancel];
    FakeTask *task = [FakeTask new];
    self.task = task;
    __weak RequestOwner *weakSelf = self;
    task.completion = ^(NSString *value) {
        RequestOwner *owner = weakSelf;
        if (!owner || ticket != owner.generation) return;
        owner.task = nil;
        owner.value = value;
        owner.updates += 1;
    };
    return task;
}
- (void)cancelCurrent {
    self.generation += 1;
    [self.task cancel];
    self.task = nil;
}
@end

static void check(BOOL condition, const char *message) {
    if (!condition) {
        fprintf(stderr, "FAIL: %s\n", message);
        exit(1);
    }
}

int main(void) {
    @autoreleasepool {
        RequestOwner *owner = [RequestOwner new];
        FakeTask *old = [owner start];
        FakeTask *current = [owner start];
        [old deliver:@"stale"];
        check(owner.updates == 0, "old result ignored");
        [current deliver:@"new"];
        check([owner.value isEqualToString:@"new"], "current result accepted");
        check(owner.updates == 1, "one accepted update");

        FakeTask *cancelled = [owner start];
        [owner cancelCurrent];
        [cancelled deliver:@"late"];
        check(owner.updates == 1, "cancelled result ignored");

        FakeTask *syncOld = [owner start];
        syncOld.completesOnCancel = YES;
        FakeTask *replacement = [owner start];
        check(syncOld.completion == nil, "cancel synchronously delivered completion");
        check(owner.updates == 1, "synchronous cancel cannot update old result");
        check(owner.task == replacement, "replacement task remains current");
        [replacement deliver:@"replacement"];
        check(owner.updates == 2, "replacement result still accepted");

        __weak RequestOwner *weakOwner = owner;
        FakeTask *retainedByTransport = [owner start];
        owner = nil;
        check(weakOwner == nil, "callback does not retain owner");
        [retainedByTransport deliver:@"after release"];
        check(retainedByTransport.completion == nil, "completion released");
        puts("PASS: stale, current, cancelled, synchronous-cancel, released-owner, completion-release");
    }
    return 0;
}

这里的关键不是代次变量的名字，而是失效发生的时机。开始新请求时，先增加代次使旧ticket失效，再调用旧任务的 cancel；用户取消时也采用这个顺序。适配器的取消方法可能在当前串行上下文中同步触发完成回调，仅仅约束线程并不能阻止这种重入。先失效后取消，才能同时拒绝同步回调和延迟回调；若取消之后才更新代次，旧结果仍有一个被接受的窗口。

示例在递交结果前清空一次性completion，既避免重复调用，也释放Block捕获的其他对象。生产代码若允许流式多次回调，则不能照搬这一点，应单独定义结束事件、订阅取消与最后一次释放。一次性请求和长连接订阅的资源模型不同。

清理本身也要通过同一个有效性检查。旧回调如果不比较代次就执行 owner.task = nil，可能把页面正在持有的新任务清掉。成功和失败可以展示不同状态，但都只能结束属于自己的当前任务；取消后的错误回调不应又把界面从“已停止”改成“请求失败”。这些约束应和业务状态机一起审查，而不是散落在几个异常处理分支中。

取消不能代替清理，清理也不能篡改结果

一种常见修补是在 dealloc 中取消请求。它可以作为最后一道防线，但如果引用环已经让对象无法进入 dealloc，这一修补不会执行。取消应放在业务生命周期结束的位置，例如搜索条件改变、页面不再拥有任务或用户明确停止；是否在页面消失时取消，要看任务是否还应在后台完成，不能统一套用。

还要区分“停止展示结果”和“撤销服务端操作”。客户端丢弃一个上传完成回调，不代表文件没有上传；取消一个支付或订单请求，更不代表服务端事务已回滚。对于有副作用的接口，应另外设计幂等键、结果查询和状态对账。UI代次只解决本地结果归属，不能承担远端一致性。

如果有多个合法并行任务，一个全局代次会过度失效。例如头像请求不该让订单列表请求失效。这时按资源或业务槽位维护token，也可以用不可变请求ID。选择整数代次是为了让本文的单槽位问题可读，不是所有并发协调器的最终设计。

验证要覆盖“还活着但已经不需要”

只测试对象释放不够。上面的程序没有睡眠和真实网络，手动控制递交顺序，使竞态可以稳定复现：先递交旧请求，再递交当前请求；取消后递交；设置旧任务在取消时立即回调，再开始替代请求；外部仍持有任务时释放所有者，最后再递交。同步取消用例同时确认旧任务确实回调过、写入次数未增加、替代任务仍是当前任务且能够正常完成，避免错误代码悄悄多写一次却恰好留下正确的最终文本。

在安装Apple命令行工具的macOS上，把代码保存为 ios_callback_lifetime.m，运行：

clang -fobjc-arc -fblocks -Wall -Wextra -Werror \
  -framework Foundation ios_callback_lifetime.m -o ios_callback_lifetime
./ios_callback_lifetime

本次以Apple Clang 21.0.0运行，六组生命周期场景检查通过，包含取消同步重入。它验证了引用和代次模型，不证明UIKit页面、实际网络取消或第三方SDK线程约定全部正确。接入真实应用后，还需用Memory Graph/Instruments观察循环与持续分配，反复进出页面，并在网络限速、连续输入和应用切后台时检查UI。工具显示某次对象已释放，也不代表每条异常路径都完成清理。

留下三条可以审查的约定

异步回调的可靠性，可以从三条具体约定开始：谁拥有任务，哪个串行上下文修改状态，什么事件使结果失效。引用关系决定对象能否结束，代次或请求ID决定结果能否生效，底层API契约决定取消与收尾如何发生。把这三件事分别写清，再决定用Block、delegate还是其他异步抽象，代码审查才有可核对的依据。
