慢查询先看执行计划：MySQL索引与游标分页的取舍

围绕租户订单列表设计组合索引、稳定排序与键集游标，解释深分页、并发插入、BIGINT 精度和执行计划的验证边界。

xq.Xiaofeng Qiao发布于 2026年10月23日本文暂时仅提供中文版本。

列表越翻越慢，先把访问路径画出来

一个订单列表按创建时间倒序显示，每页五十条。第一页很快，第两千页明显变慢。增加接口超时只能让用户等得更久；给每个过滤字段都加单列索引，也未必形成想要的访问路径。

先把问题写成一条明确的查询：限定租户、限定订单状态，按时间和唯一编号排序，拿下一批记录。本文以 2016 年 MySQL 5.7 时代的列表查询为回顾视角，示例是独立分析。当前官方主站的部分 5.7 链接会跳到新版手册，因此历史语义使用 Oracle 保留的 5.7 手册核对，不把新优化器功能倒放进早年设计。MySQL 5.7 组合索引说明

索引顺序应当服务一条查询

教学表保留列表真正需要的字段：

CREATE TABLE blog_demo_orders (
  id BIGINT UNSIGNED NOT NULL PRIMARY KEY,
  tenant_id BIGINT UNSIGNED NOT NULL,
  status VARCHAR(16) NOT NULL,
  created_at DATETIME(6) NOT NULL,
  total_minor BIGINT NOT NULL,
  KEY ix_feed (tenant_id, status, created_at, id)
) ENGINE=InnoDB;

前两个字段用于等值限定，后两个字段表达列表顺序。组合索引的价值在于有序地缩小访问范围，而不是“包含了查询出现过的所有字段”。如果另一个页面不传 tenant_id，这份索引就不能被简单当作同样有效的查找入口；是否新增索引，要根据另一条查询的频率和代价判断。5.7 的组合索引查找遵循最左前缀规则，不能仅因为条件里出现索引的后半段就认定会有效定位。最左前缀与索引列顺序

这里没有把金额也放入索引。读取 total_minor 可能仍需回到表记录；是否值得做覆盖索引，要权衡列表频率、字段宽度和写入成本。一个只用于展示的长文本字段，不值得为了消除少量回表就塞进每个索引页。对“查询快了”的评估，也要包含订单插入和状态变更的成本。

OFFSET 与游标解决的是不同交互

页码分页适合数据规模有限、用户需要直接跳到某页的后台。深度偏移则要求数据库找到前面的候选记录再丢弃许多行，索引并不会让被跳过的记录完全消失。对于“继续加载下一批”的信息流，可以把上一页最后一条记录的位置作为边界：

SELECT id, created_at, total_minor
FROM blog_demo_orders
WHERE tenant_id = 7 AND status = 'open'
ORDER BY created_at DESC, id DESC
LIMIT 50;

假设末条的时间和编号是游标中的值，下一页使用严格小于的字典序：

SELECT id, created_at, total_minor
FROM blog_demo_orders
WHERE tenant_id = 7 AND status = 'open'
  AND (created_at < '2016-05-01 10:00:00.000001'
       OR (created_at = '2016-05-01 10:00:00.000001'
           AND id < 9007199254740995))
ORDER BY created_at DESC, id DESC
LIMIT 50;

真实接口应使用驱动参数绑定，不拼接游标输入。时间相同的订单很常见，必须增加唯一编号作为决胜字段，否则数据库可以在并列记录之间改变顺序，翻页就可能重复或漏项。时间列与编号都设为非空，避免再引入空值排序的特殊分支。

在固定前缀条件下，5.7 有机会利用索引满足两个字段同方向的倒序读取。它不是“只要有索引就一定不排序”：额外字段回表、选择性与优化器估算都可能改变计划。混合升降序也应单独验证，不能把新版物理降序索引的能力直接套进 5.7。5.7 ORDER BY 优化

游标必须携带查询身份

游标至少包含时间、编号、排序方向和过滤条件的版本。用户从 open 切换到 closed 时，应重新从第一页开始，而不是沿用旧游标。多租户接口还要以服务器鉴权身份重新限定租户，不能让游标成为修改查询归属的入口。

可把这些字段编码成不透明令牌并签名，阻止调用者随意改写边界；签名不等于加密，也不能替代鉴权。游标有效期、字段版本与页面大小上限都应有明确规则。编号如果是数据库 BIGINT，经 JavaScript 中转时要避免先转成 Number 再序列化，超过安全整数范围后相邻编号可能变成同一个数。示例模型用十进制字符串承载编号，只在比较时转为 BigInt。

游标也不是数据库快照。第一页之后插入的新订单如果排在边界前，继续翻旧页时不会看到它；这适合向后浏览，但需要“刷新查看新内容”的交互。如果现有记录的排序字段、状态被修改，它可能跨越边界。要求完整导出或审计快照时，应采用固定结果集、合适的快照策略或独立导出任务，不能用信息流分页作完整性承诺。

字段、参数和时间必须说同一种语言

列表按天过滤时，尽量先在应用层算出明确时区的起止边界，再用 created_at >= start AND created_at < end 表达区间。把列包进 DATE(created_at) 虽然容易读，却可能让原本直接作用于索引列的范围条件变成函数计算；具体影响要看目标版本和执行计划，不能凭写法漂亮就认定等价高效。

游标序列化还要保留数据库实际使用的时间精度。若把微秒截成秒，同一秒内的记录会被错误地划进边界；若页面展示本地时间、游标却没有注明转换规则，也可能把夏令时或时区偏移带回查询。索引解决不了这些数据契约错误。接口日志可以记录游标版本与边界摘要，用于定位漏页，但不必把可识别用户的完整过滤条件长期写进日志。

看 EXPLAIN 时，先回答三个问题

在一次性测试库准备有代表性的数据后，分别对首页、较深 OFFSET 页和游标页执行普通 EXPLAIN。先看实际选中的 key，再看估计访问行数 rows、过滤比例 filtered 与 Extra。possible_keys 只是候选索引，rows 是估计而不是实际扫描计数；Using filesort 说明存在额外排序步骤，不能仅凭名字推断一定发生磁盘排序。5.7 EXPLAIN 输出

验证数据要包含大租户、小租户、稀有状态、相同时间戳和深页，不能只测几十条均匀数据。记录结果数量、顺序、响应分位数和写入代价，再讨论是否采用索引。执行计划选错也可能来自数据分布或统计信息，不宜先用索引提示永久压住症状。这里不使用后续版本的 EXPLAIN ANALYZE 来声称 2016 年已有该能力。

本次没有安装或连接 MySQL，因此附带 SQL 的语法执行、索引选择和性能均未实测。examples/keyset_model.mjs 在 Node.js 16.16.0 执行通过七组行为检查：完整遍历、同时间决胜、超出安全整数的编号、并发插入较新项、删除游标锚点、拒绝跨过滤条件游标及页面大小限制。它验证排序与边界算法，不模拟 B-tree 或优化器，不能作为性能提升证据。

结论

分页优化先从交互与查询条件出发。组合索引缩小查找范围，唯一决胜字段让顺序明确，游标让后续页从已知位置继续；它们都不自动提供全局快照。把正确性、访问计划和真实负载分开验证，才能知道一次优化究竟减少了哪些工作，又付出了什么代价。
