Java异步任务：CompletableFuture、线程池与超时传播

从一个有界线程池出发，说明异步组合、队列饱和、等待超时和底层工作取消为什么是四个不同问题。

xq.Xiaofeng Qiao发布于 2026年10月23日本文暂时仅提供中文版本。

异步链变短以后，排队却可能变长

一个聚合接口先获取商品，再查询库存与配送信息。把顺序调用改成 CompletableFuture 后，代码更像一条流程，但这不等于系统就拥有了更多可用连接。线程、任务队列、数据库连接和下游服务仍各有上限。

本文以 2017 年常见的 Java 8 能力为回顾基线，讨论如何把异步任务放进可控的资源边界。代码使用 Java 8 API，在本机 Corretto 11 上通过 javac --release 8 编译并执行；没有把后来的 orTimeout、虚拟线程写进早期实现。

首先区分四件事：future 怎样组合，工作在哪个 executor 运行，调用方愿意等多久，以及底层操作能否停止。把它们揉成一个“异步超时”开关，通常会留下看不见的后台工作。

显式选择执行器，是在划定故障范围

不传 executor 的异步方法会采用默认执行设施。若把阻塞 I/O 和其他共享任务混在一起，一个慢依赖可能影响不相关的流程。官方文档对默认 executor 的行为有明确约定。CompletableFuture Java 8 文档

对依赖聚合，示例显式建立一个工作线程、一个排队位置的池。这组很小的数字用于让饱和行为可复现，不是生产配置建议：

ThreadPoolExecutor executor = new ThreadPoolExecutor(
    1, 1, 0L, TimeUnit.MILLISECONDS,
    new ArrayBlockingQueue<Runnable>(1),
    new ThreadPoolExecutor.AbortPolicy()
);

有界队列把等待空间变成可观察的资源。第三个任务到达时，若一个正在运行、另一个仍在排队，就应该有明确结果，而不是持续堆积直到内存或请求期限耗尽。真实配置应依据依赖容量、任务耗时和容许排队时间确定，还要观测队列长度、拒绝数量及排队延迟。

线程池不是越大越保险。如果下游只允许少量并发请求，增加线程只会把阻塞从本地队列移动到远端。不同依赖通常需要分别限制，避免某一个慢服务占满全局执行能力。

拒绝也必须进入异步结果

示例把提交行为包装成以下方法。它既接收执行中的异常，也接收提交阶段的饱和拒绝，避免调用方拿到一个永远不会完成的 future：

static <T> CompletableFuture<T> submit(
        Executor executor, Supplier<T> work) {
    CompletableFuture<T> output = new CompletableFuture<>();
    try {
        executor.execute(() -> {
            try { output.complete(work.get()); }
            catch (Throwable error) {
                output.completeExceptionally(error);
            }
        });
    } catch (RejectedExecutionException rejected) {
        output.completeExceptionally(rejected);
    }
    return output;
}

此处捕获任务错误，是为了让等待者观察失败，而不是把严重错误解释成正常业务结果。真正的服务还需要针对致命运行时错误制定进程级策略。这段包装也没有自动建立底层任务的取消桥接，不能因为返回类型是 future，就推断它能停止任意 supplier。

拒绝策略尤其不能只看名字。静默丢弃任务可能让包装的结果一直未完成；在调用线程执行虽然能产生压力反馈，但若调用者是事件循环，就可能把阻塞带回最不该阻塞的位置。示例选择显式拒绝，把容量不足交给上层决定重试、降级还是返回服务繁忙。线程池排队与拒绝规则

组合依赖，不要把线程池锁在等待里

如果下一步也返回 future，应使用组合操作表达依赖，而不是在工作线程里提交后再 join()：

CompletableFuture<Integer> chain = submit(executor, () -> 20)
    .thenCompose(n -> submit(executor, () -> n + 1))
    .thenApply(n -> n * 2);

当唯一工作线程阻塞等待队列里的子任务时，子任务没有机会执行。扩大池也只能改变死锁出现的规模。组合操作让父阶段结束后释放线程，后续阶段再按执行器的资源边界调度。

thenApply 适合把已经取得的值转换为新值；返回另一个 future 的函数则需要考虑展平依赖。还要区分普通回调与异步回调：不要把耗时解析放进一个看似便宜、实际上可能由完成线程执行的回调里。接口组合和线程安排是相关但独立的设计。

超时等待，不等于工作已经取消

get(timeout, unit) 限制的是当前调用者等待结果的时间。示例让 supplier 等待一个闩锁，确认等待超时后 future 仍未完成，再释放闩锁，任务依然可以返回结果。

同样，CompletableFuture.cancel(true) 不能被当作对 supplier 执行线程的可靠中断请求。Java 8 的文档说明它没有直接控制产生结果的计算，取消属于异常完成。配套测试单独验证了这一点，不能把取消标志和真实工作退出混为一谈。

生产调用需要把剩余预算传给底层：连接建立、读取和数据库语句各自配置期限，并在资源取得后及时关闭。多个步骤不要每一步重新获得完整超时时间，否则总耗时会超过请求预算。重试也应消耗同一个预算，而不是让失败路径无限延长。

预算还包含排队时间。一个任务等待了大部分期限之后才取得线程，即使下游允许较长读取超时，也未必值得继续执行。实际服务可以在开始 I/O 前再次检查截止时间，对剩余预算不足的任务直接返回可识别的失败。容量不足后立即无间隔重试，则会把拒绝变成更多流量，需要由上游采用有上限的退避或停止策略。

降级不能把未知写成业务事实

在链尾用 exceptionally 返回默认值很方便，但默认值必须有真实业务含义。“库存未知”不能降级成库存为零，“配送服务超时”也不等于该地区无法配送。更合适的聚合结果会保留各字段的状态、来源和可重试条件，让界面准确说明哪些部分暂不可用。

这种区分还影响缓存：正常业务结果可以按约定缓存，依赖故障产生的临时降级值不应无差别写进同一长期缓存。否则下游已经恢复，用户仍会继续看到被缓存的假阴性。异常处理既是线程问题，也是数据语义和恢复策略的一部分。

用控制信号重现饱和，而不是依靠睡眠

配套程序先等待第一项任务实际进入 supplier，再提交第二项使队列占满，最后检查第三项以拒绝异常完成。这个顺序使用 CountDownLatch 控制，避免猜测线程调度速度。

它还执行正常组合、等待超时不取消任务、逻辑取消不中断 supplier 四组检查。退出时释放闩锁、停止线程池，并等待线程池结束，测试本身不留下常驻工作。

javac --release 8 BoundedFutures.java
java BoundedFutures

本机实际使用 Corretto 11.0.23 执行，检查通过。--release 8 用于约束 API 与目标字节码，不等于已经在 Java 8 运行时验收；真实 HTTP、数据库驱动和高负载环境也不在这份离线检查范围。

异步接口需要同时表达结果和容量

一条容易维护的异步链，不只是成功路径简洁。它应该能说明任务被谁执行、最多排多少、拒绝怎样表达、超时后谁还在工作，以及退出时资源由谁回收。先把这些问题回答清楚，再讨论增加并发，通常比盲目调整线程数更有效。
