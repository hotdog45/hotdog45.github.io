Hooks中的旧闭包与请求竞态：让Effect拥有清理责任

通过搜索结果乱序返回分析闭包、依赖、结果归属与清理，构造可控 Promise 验证旧请求不会覆盖当前选择。

xq.Xiaofeng Qiao发布于 2026年10月23日本文暂时仅提供中文版本。

最后返回的请求，不一定属于最后一次选择

用户先点开 A 商品，随后切换到 B。B 请求很快返回，页面显示 B；稍后 A 请求才完成，又把内容覆盖成 A。页面标题来自当前选择，详情却来自旧请求，单看每次网络调用都没有报错。

本文以 React 16.8 稳定引入 Hooks 的 2019 年为回顾起点，用独立分析示例解释异步结果归属。代码只使用 useState、useEffect 等该时期已有的接口，行为模型在今天的 Node.js 16.16.0 运行。当前 React 文档中的后续 API 与开发模式检查不会被当作 2019 年已有的默认行为。React 16.8 发布记录

闭包保存的是一次渲染所看到的值

函数在一次渲染中创建，引用的状态和参数也属于那次渲染。一个只在首次建立的定时器，如果回调持续使用当时的 count，就不会因为界面重新渲染而自动换成新值。这不是“React 忘了刷新变量”，而是 JavaScript 闭包与 React 渲染模型共同产生的结果。

如果更新只依赖前一个计数值，可以采用 setCount(previous => previous + 1)。但这不能替代所有依赖：回调若还读取当前房间、筛选条件或权限，仍需决定何时重新建立外部连接。把依赖数组随意改成空数组，只是让过期引用不再明显地重新执行，并没有使它变正确。旧版 Effect 使用说明

对商品查询，更直接的不变量是：只有仍然属于当前那次 Effect 的结果可以更新页面。旧请求可以完成，但失去修改当前界面的资格。把“能否更新 UI”与“能否真正终止远端工作”分开，设计会清楚许多。

让每次 Effect 拥有自己的结果许可

先把异步操作抽成一个小函数，返回清理动作：

function beginLoad(id, load, publish) {
  let active = true;
  publish({ id, status: 'loading', data: null, error: null });
  const done = Promise.resolve().then(() => load(id)).then(
    data => {
      if (active) publish({ id, status: 'success', data, error: null });
    },
    () => {
      if (active) publish({ id, status: 'error', data: null, error: 'load_failed' });
    }
  );
  return {
    done,
    cleanup() { active = false; }
  };
}

Promise.resolve().then(() => load(id)) 也会把加载函数的同步抛错送进失败分支。错误显示使用公开的错误码，而不是把接口堆栈直接写进页面。清理后，成功与失败分支都检查许可；不能只挡住成功回调，却让旧请求的错误提示盖住新页面。

在 Hook 中连接它：

import { useEffect, useState } from 'react';

function useResource(id, load) {
  const [state, setState] = useState({
    id, status: 'loading', data: null, error: null
  });
  useEffect(() => {
    const operation = beginLoad(id, load, setState);
    return operation.cleanup;
  }, [id, load]);
  return state.id === id ? state : {
    id, status: 'loading', data: null, error: null
  };
}

这里假定 id 是已校验的非空资源请求键，完整区分资源及其业务作用域，load 返回该键对应的数据或拒绝 Promise。load 应放在组件外，或用合适的 useCallback 维持身份；在每次渲染里创建新函数，再作为依赖传进来，会使 Effect 不断重新建立。正确做法是调整数据流和函数边界，而不是删掉真实依赖压住症状。当前 useEffect 依赖说明

返回前的 state.id === id 也有作用。选择已变成 B 时，新 Effect 尚未运行的那次渲染仍可能保存 A 的旧状态；直接把它画出来，会短暂显示错配数据。把状态绑定到资源标识，可以在这一阶段先展示加载态。若产品希望保留旧数据作为过渡，应明确标记正在刷新，而不是让旧详情看起来属于 B。

清理不是一键取消所有副作用

依赖变化后，React 会先清理旧 Effect，再执行新的建立逻辑；组件移除时也会清理。因此局部许可可以把一段外部同步工作限制在它对应的生命周期内。useEffect 建立与清理顺序

这个例子没有取消网络请求，只是丢弃已经失去归属的结果。实际 fetch 可以结合受支持环境中的取消机制节约资源，但请求已经到达服务端后，取消客户端等待不等于回滚服务端操作。查询与写入也不同：保存订单不应仅由某个渲染 Effect 隐式触发，否则重新建立同步过程就可能重复产生业务副作用。

订阅还需要对称地解除订阅，定时器需要清除定时器。不能因为已经加了 active 布尔值，就忘记释放持续占用资源的连接。结果忽略负责 UI 正确性，资源清理负责生命周期，两者相关但并不互相替代。

用可控 Promise 制造坏顺序

只用一个立即返回的 mock，几乎一定测不出竞态。应让测试自己控制 A、B 请求何时完成：先启动 A，清理 A，再启动 B；先完成 B，最后才完成 A。最终界面状态仍必须属于 B。

随稿 examples/effect_races.mjs 已在 Node.js 16.16.0 完成七组检查：旧成功结果被忽略、只有当前请求发布成功、资源标识不匹配时显示加载、匹配时保留数据、清理后旧失败不再更新、同步异常进入失败分支、失败输出使用公开错误码。没有定时等待或真实请求，执行顺序由 Promise 控制，重复运行结果可预测。

这不是 React 渲染器集成测试，也没有验证浏览器取消请求、Suspense 或框架的数据缓存。接入实际组件后，还要检查快速切换、卸载、重新挂载和相同资源多次刷新。当前 Strict Mode 会增加开发期的 Effect 检查，适合暴露不对称清理；这是今天调试时的补充，不能据此解释为 2019 年所有版本都会执行同样检查。当前 Strict Mode 文档

请求身份比商品编号更完整

两个租户可能拥有相同的商品编号，权限切换后同一个地址也可能返回不同内容。因此请求键不一定只是数据库主键，还可能需要租户、语言和权限版本。若用户身份改变而键完全不变，旧数据就可能在新 Effect 启动之前被继续展示。应在上层把真正影响结果归属的作用域纳入请求身份，并在权限失效时撤销对应数据；不要把访问令牌明文拼进可记录或持久化的键。

当依赖修正导致频繁重连，也要检查是不是把多份职责塞进了一个 Effect。例如数据订阅负责连接生命周期，界面上的排序可以由当前数据直接推导；为了改变排序就断开重连，会放大网络负担。定时回调只需要累积消息时，可以通过函数式状态更新读取前值，但连接到哪个租户和房间仍需明确依赖。减少不必要的外部同步，与隐瞒真实依赖，是两种完全不同的修改。

数据获取方案也有边界

这个小 Hook 适合说明结果归属，不具备跨组件去重、缓存失效、预加载或服务器渲染的数据协调能力。当多处页面读取同一资源，继续堆局部 Effect 容易出现重复请求和瀑布等待。可以选择成熟的数据层或框架加载机制，但仍应验证它如何定义请求键、权限变化与旧结果失效，不能只把问题交给库名。

结论

处理 Hooks 竞态，先回答“结果现在属于谁”。依赖描述何时需要重新同步，清理撤销旧同步的许可，资源标识决定当前渲染能展示什么。把这三层约定拆开，再主动制造乱序结果，就能用可复现的证据判断修复是否成立。
