Java虚拟线程：I/O并发增加后，数据库连接池怎么办

把虚拟线程的调度能力与下游容量分开，使用有期限的许可控制、入口限流和可验证的资源归还保护服务。

xq.Xiaofeng Qiao发布于 2026年10月23日本文暂时仅提供中文版本。

线程变便宜，连接却没有变多

把请求处理改成虚拟线程后，原来受线程数限制的代码可能同时发起更多数据库调用。应用侧看起来不再缺线程，数据库连接池却开始排队，用户等待反而变长。

这并不矛盾。虚拟线程改变了等待任务占用执行线程的成本，没有替数据库增加连接、CPU或事务吞吐。本文回顾Java21在2023年正式提供的能力，重点讨论下游资源背压。以下分析按Java21语义展开；后续JDK优化需要按对应版本重新评估。

Oracle的Java21说明强调虚拟线程主要面向大量等待I/O的任务，不是让单次计算本身更快。Java21 Virtual Threads

不再用线程池间接代表数据库容量

传统线程池常同时承担两种角色：复用昂贵线程，以及限制同时执行的任务。迁移到虚拟线程时，如果照搬一个“小型虚拟线程池”，会把两件事继续绑在一起。

更清楚的设计是：执行器按任务提供虚拟线程，而数据库调用、第三方接口和CPU重任务各自有容量边界。一个请求可能不访问数据库，另一个请求可能持有连接更久，它们不该因为线程模型相同，就被当成同一种资源消耗。

同样，不应把数据库连接保存在每个线程的ThreadLocal中，假定线程数量始终很少。数量增长后，原来的隐式缓存可能变成大量资源持有。连接应由连接池管理，在明确的作用域内获取并归还。

用许可表达“最多同时占用多少依赖”

配套PermitGate把依赖容量表示为Semaphore，而不是虚拟线程的数量：

public <T> T call(long waitMillis, Callable<T> work) throws Exception {
    if (!permits.tryAcquire(waitMillis, TimeUnit.MILLISECONDS)) {
        throw new RejectedExecutionException("capacity exhausted");
    }
    try { return work.call(); }
    finally { permits.release(); }
}

只有实际拿到许可才进入finally归还，避免未取得资源时误释放。等待许可有上限，错误也保留为容量不足，而不是伪装成正常空结果。示例开启公平队列只是便于表达顺序意图，不构成跨请求、跨租户的完整公平调度保证。

Java21调用侧可以使用每任务虚拟线程执行器：

PermitGate database = new PermitGate(2);
try (ExecutorService tasks = Executors.newVirtualThreadPerTaskExecutor()) {
    Future<String> result = tasks.submit(
        () -> database.call(100, () -> "fixture-row")
    );
    System.out.println(result.get());
}

这里的2和100毫秒是离线示意参数，没有经过生产容量测量；返回值也是固定夹具，不是数据库查询。真正的许可数量应与连接池、查询类型和下游预算共同设计，不能把示例数字直接当成最佳实践。

容量门之外，还需要入口边界

Semaphore限制了正在使用依赖的任务，却可能留下大量等待许可的任务。若接口无限接收请求，仍会积累请求体、future、日志上下文和超时状态。线程便宜不代表这些对象没有成本。

因此需要同时考虑入口最大在途请求、队列长度、请求大小和等待期限。过载时及时拒绝，通常比让所有人等待到超时更可控。拒绝后若上游立即重试，又可能放大负载；客户端退避与服务端容量信号应该共同设计。

多个资源也不能随意嵌套占用。先拿数据库许可，再长时间等待远端API，会把两个依赖的容量绑成一个系统性瓶颈。可以缩小持有区间，先完成不需要连接的工作，再开启尽可能短的事务；必要时采用异步状态流程，而不是持着事务等待人工或网络。

超时预算要覆盖排队和实际操作

许可等待、连接获取、SQL执行和结果读取，共用一次请求的剩余预算。如果每个阶段都重新获得完整超时，最终请求可能明显超过调用方容许时间。

而且等待者超时不代表底层语句已经停止。应结合驱动的取消与语句超时能力，并验证连接能否安全复用。对于结果未知的写操作，需要业务操作标识和状态查询，不能凭一个TimeoutException直接再次写入。

这也是为什么迁移验收不能只比较请求总数。应分别测量许可等待、连接等待、查询执行、错误率和资源归还情况，才能判断瓶颈是真的消失，还是换了位置。

Java21的pinning要按版本和调用链定位

在Java21中，一些阻塞场景会让虚拟线程不能从carrier上卸载，例如相关的synchronized或native调用路径。它影响可扩展性，不意味着所有使用synchronized的代码都必须机械替换。

应先观察实际长时间阻塞在哪里，再缩小锁范围或采用适当的锁机制。Java21提供的JFR虚拟线程事件可用于定位；这些约束不能不加版本说明地推广为所有未来JDK的固定结论。迁移时还应核对数据库驱动、监控和诊断工具的对应版本，而不只替换执行器一行代码。

本机验证了许可模型，没有运行Java21

本机可用的是JDK8与JDK11，未安装新工具链。配套把PermitGate和平台线程测试以Java8兼容目标在Corretto11.0.23编译执行，验证了两个许可占满时第三次调用被拒绝、成功后归还许可、异常后不泄漏，以及恢复后仍可继续调用。

javac --release 8 PermitGate.java PermitGateTest.java
java PermitGateTest

测试使用闩锁确定占用状态，没有靠睡眠猜测并发时序。独立的VirtualGate.java按Java21官方API审阅，但未在本机编译或运行。上述通过结果只证明共享的容量控制逻辑，不能称为虚拟线程性能、pinning或驱动兼容性验证。

具备Java21环境后，还需要运行虚拟线程分支、接入受控数据库做负载和取消测试，并比较迁移前后的同一组业务指标。没有这些结果，不应把“支持更多任务”写成虚构的吞吐提升比例。

调度机制与业务容量要分别治理

虚拟线程让同步风格的I/O代码有了新的扩展空间。可靠迁移的重点，是把过去由线程数隐含控制的资源约束显式化：入口限制、依赖许可、请求期限和资源归还分别可见。这样才能利用新的调度能力，而不把压力直接传给下游。
