长流程任务的恢复：持久化状态、补偿与重复执行

从等待审批到跨系统效果，把恢复位置、未知结果与补偿进度写进可验证的持久化状态机。

xq.Xiaofeng Qiao发布于 2026年10月23日本文暂时仅提供中文版本。

一个等待审批的流程，不能靠函数栈活着

考虑一项模拟资源开通任务：先等待审核人确认规格，再预留资源，最后激活。审批可能隔天才到；工作进程可能在预留成功后重启；激活失败以后，还要归还属于本任务的预留。把这三步写在一个长函数里，再在异常处调用取消，无法回答恢复时最重要的问题：哪一步已经产生效果，哪个决定仍然有效？

本文是 2026 年编写、面向 2025 年长流程工程主题的分析示例。使用 Python 3.9 兼容代码与两个临时 SQLite 数据库，分别模拟编排器和资源提供者；不连接实际云资源。示例故意保留两个提交边界，避免在一个事务里假装解决了跨系统一致性。

状态描述下一步允许做什么

状态集合要能指导恢复，而不仅是给页面配颜色。WAIT_APPROVAL 表示不能调用资源服务；RESERVE_PENDING 表示审批已保存，可以尝试预留；ACTIVATE_PENDING 表示可以继续激活；RECONCILE 表示效果未知，需要查询；COMPENSATE_PENDING 表示补偿尚未完成。DONE、CANCELLED、EXPIRED 是本例终态。

WAIT_APPROVAL → RESERVE_PENDING → ACTIVATE_PENDING → DONE
       ↓                               ↓           ↑
    EXPIRED                         RECONCILE ──────┘
                                       （查询确认激活）
ACTIVATE_PENDING → COMPENSATE_PENDING → CANCELLED
                   （明确拒绝后释放自己的预留）

RECONCILE 没有直接通向取消的箭头：超时只说明没有收到确定答复。实际已经激活的资源，不能因为编排器着急收尾就按“预留失败”释放。查询仍不可用时，流程停在可解释的等待状态，交给运维恢复查询或人工核对。

审批绑定输入，恢复不扩大授权

示例保存工作流 ID、输入摘要、修订号、审批人、审批截止时间和当前状态。审批入口比较摘要与修订号，并在同一数据库事务中保存审批结果和下一状态。同一个 ID 的规格改变会被拒绝；新规格需要新的版本与审批。

if row['state'] != 'WAIT_APPROVAL' or row['spec_hash'] != spec_hash or row['revision'] != revision:
    raise ValueError('stale approval')
if now >= row['expires']:
    self._state(flow, 'EXPIRED', 'approval deadline')
    return 'EXPIRED'
self.db.execute('UPDATE flows SET approver=? WHERE id=?', (actor, flow))
self._state(flow, 'RESERVE_PENDING', 'approved exact revision')

这段摘录位于事务上下文内，完整代码见随文示例。actor 必须由已认证的宿主入口提供；本地固定审核人只是测试夹具，不是可部署的身份认证。这里的期限是“接受审批的期限”，并未实现执行窗口或后续撤销授权；若业务需要这些语义，应另建状态与校验，不能从一个 expires 字段推导全部权限。

最危险的窗口在两次提交之间

预留操作采用稳定键 job-7:reserve:v1。提供者先提交自己的数据库，编排器随后才把状态改为 ACTIVATE_PENDING。测试在这两步之间主动抛出异常，再关闭并重新打开两个连接。恢复看到的仍是 RESERVE_PENDING，因而重发同一个操作键；提供者返回既有预留，不再增加资源。

本地日志写了“准备调用”不能证明外部调用成功；日志写了“调用失败”也不能证明外部没有效果。稳定键的有效期、同键输入冲突规则、查询接口的可信度，都是提供者契约的一部分。若真实服务不支持它们，就需要额外的对账或人工处理路径，不能只在编排器中加一个 done 字段。

SQLite 能把单个数据库中的状态与历史记录一起提交，但不会让另一个数据库自动参与同一原子事务。示例的每条状态转换同时追加历史，方便解释“为什么现在在这里”；资源操作放在这些短事务之外，不持有数据库写锁等待远端响应。SQLite 事务文档说明了事务和单写者边界。

补偿是新的业务动作，也可能失败

激活接口明确返回 rejected 时，夹具契约保证激活没有发生，才转入补偿。释放动作只允许把本工作流预留从 reserved 改为 released，不会恢复整个资源表的旧快照，也不会触碰其他工作流。补偿异常时保留 COMPENSATE_PENDING，下次仍从这里尝试。

elif state == 'COMPENSATE_PENDING':
    self.provider.release(op)
    with self.db:
        self._state(flow, 'CANCELLED', 'owned reservation released')

如果释放已成功而本地尚未记录，重试释放也必须安全。示例提供者允许重复释放，并检查最终状态。工程上还要区分不可逆步骤，确定哪些取消需要业务批准。微软的补偿事务模式强调补偿与领域规则有关，补偿本身也要记录进度并可恢复；它不等价于数据库回滚。

另一条失败路径是“激活已提交，但答复丢失”。本例进入 RECONCILE，查询到 active 才完成；查询返回空或仍为预留时也不会擅自补偿，因为真实提供者可能存在传播延迟。生产系统应定义查询的一致性、最长等待与人工裁决入口，避免无限沉默。

怎样验证恢复，而不只验证正常顺序

完整示例位于 examples/durable-workflow/，在临时目录内运行：

cd examples/durable-workflow
/usr/bin/python3 -m unittest -v

实际使用 Python 3.9.6 执行 6 项测试，通过情况包括：等待审批跨重启后仍无外部效果；变更输入、旧修订和非审核人被拒绝；预留提交窗口中断后仅留一个效果；补偿失败后重启继续；激活答复丢失先等待查询；终态重复推进不追加历史。测试还确认另一个工作流仍处于自己的等待状态。

这些是受控故障与连接重开验证，未验证断电、磁盘损坏、多工作进程竞争或真实远端服务。扩展到多执行者时，需要抢占租约、版本比较及过期执行者隔离；仅靠 SQLite 单写者无法保证同一个业务任务不会被两个进程同时推进。

什么时候引入成熟工作流引擎

只有少量审批与一个受控提供者时，显式状态表更容易审查。步骤多、等待长、计时器与部署版本兼容复杂时，成熟引擎能降低自建调度成本。Temporal 的官方文档解释了事件历史与重放如何支撑恢复；本文并未运行 Temporal，也不把这里的简单状态机称作它的等价实现。Temporal 执行与重放说明

恢复设计的验收标准，是进程消失后仍能回答“下一步允许做什么、已有哪项可信效果、哪些需要核对”。把审批、未知结果与补偿进度保存下来，任务才有清楚的继续位置。
