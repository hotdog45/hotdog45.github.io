Vue 3 与 TypeScript：把后台页面的隐式状态变成明确约定

从订单审核页出发，拆分筛选条件、服务器快照和编辑草稿，处理请求竞态、版本冲突与组件事件，让类型真正帮助协作。

xq.Xiaofeng Qiao发布于 2026年10月23日本文暂时仅提供中文版本。

一个审核页，为什么会有三份“订单状态”

订单列表显示“待审核”，详情抽屉已经被改为“通过”，顶部数量却没有变化。这类问题不一定来自响应式失效，而是同一个词被用来描述三种东西：服务器上已经保存的结果、用户正在修改的草稿，以及由当前筛选条件计算出来的列表。

后台页面变复杂以后，我会先给这些状态划分所有权，再决定拆几个组件、用不用全局 store。组件数量无法说明一致性；一份对象被更多地方引用，也不代表大家对它有相同的修改权。

本文以 Vue 3 的 Composition API 和 TypeScript 为讨论基础，按 2022 年的技术阶段回顾后台页面设计。示例是独立构造的审核流程，不对应某个客户系统，也不依赖后来增加的 Vue 3.5 API。

让状态先表达业务，再表达组件

可以把页面拆成四层：路由中的查询身份、服务端返回的只读快照、抽屉内可丢弃的草稿，以及提交期间的状态。列表条目被打开时，复制需要编辑的字段；关闭抽屉不应该顺便把列表的原对象改掉。

type ReviewDraft = {
  orderId: string
  expectedVersion: number
  decision: 'approve' | 'reject'
  reason: string
}

type SaveState =
  | { kind: 'idle' }
  | { kind: 'saving'; requestId: string }
  | { kind: 'conflict'; currentVersion: number }
  | { kind: 'failed'; message: string }
  | { kind: 'saved'; version: number }

这比 loading、success、hasError 三个布尔值更容易审查：一种状态里有哪些字段，是类型的一部分。渲染时先判断 kind，再访问对应内容；新增分支也更容易被编译器提醒。TypeScript 的联合类型与收窄支持这类建模，但无法替服务端验证传入的数据。

不需要把每个输入字符都做成复杂状态机。重点是不能同时成立的业务阶段，以及阶段之间需要保留的信息。筛选后的总数适合从当前数据派生，用户尚未提交的理由则需要独立保存。把派生值再复制进 store，往往只增加同步任务。

请求返回时，还要检查它属于哪次选择

用户从订单 A 切到 B，A 的详情后返回，不能覆盖 B。只看 orderId 还不完整：同一订单换租户、权限或数据版本时，查询身份也改变了。

Vue 的 watcher 提供清理回调。下面用与 watcher 绑定的失效标记保护结果，并尝试中止不再需要的请求：

watch(queryKey, async (key, _previous, onCleanup) => {
  let active = true
  const controller = new AbortController()
  onCleanup(() => {
    active = false
    controller.abort()
  })
  loadState.value = { kind: 'loading' }
  try {
    const snapshot = await loadOrder(key, controller.signal)
    if (active) loadState.value = { kind: 'ready', snapshot }
  } catch (error) {
    if (!active) return
    loadState.value = { kind: 'failed', message: describe(error) }
  }
}, { immediate: true })

queryKey、loadState、loadOrder 和 describe 是应用提供的类型化接口；这是组合函数的核心片段，不是完整组件。失效标记解决的是结果归属，中止信号用于减少无用工作。服务端可能已经接收请求，所以不能把浏览器取消解释为业务操作已撤销。Vue watcher 文档解释了副作用清理；此处使用回调参数形式，不使用 3.5 才增加的 onWatcherCleanup。

还要小心 finally 中的 loading = false：旧请求的 finally 也会执行，可能把新请求的加载提示关掉。把加载状态纳入同一份请求所有权检查，比逐个补丁更可靠。

Props、事件和接口响应是三种不同的边界

详情组件通过 props 接收快照，通过事件提出保存意图。它不应该偷偷修改父组件的订单对象，也不应该直接把弹窗内的全部表单字段当成 API 请求。

const emit = defineEmits<{
  (event: 'submit', draft: ReviewDraft): void
  (event: 'close'): void
}>()

事件约束可以帮助调用方发现字段缺失，具体写法见 Vue 与 TypeScript。但给 response.json() 写一个 as Order 只是类型断言，不会检查真实响应。网络边界仍要验证对象形状、枚举、版本号和必要字段，再进入页面状态；错误响应不能因为“类型写对了”而被当成订单。

权限同样不能放在前端类型里解决。按钮隐藏是交互提示，服务端必须按当前身份和当前订单状态重新检查可操作性。审核人的备注、内部字段和操作凭据也不应该由一个通用对象穿过所有组件。

保存冲突时，保留草稿比自动覆盖更有用

提交请求携带 expectedVersion。服务端只在版本仍符合时修改，并返回新的快照；冲突时返回明确结果和当前版本。前端保留审核理由，提示重新查看差异，而不是默默覆盖其他人的判断。

保存成功后的列表刷新也有两种合理策略：更新已确认的那一项，或重新获取当前筛选结果。如果审核后条目不再符合“待审核”筛选，应按产品约定移除、短暂标记，或保留到下一次刷新。最差的状态是局部修改了条目，却继续展示未经重新计算的总数。

请求超时时，应显示“结果尚未确认”，并允许查询回执。再次提交是否使用原请求号，要由服务端的幂等约定决定。每次点击重新生成业务请求号，会把网络重试变成第二次审核意图。

用坏顺序检验设计是否站得住

最有价值的回归用例通常不是“点按钮出现成功提示”，而是这些交错顺序：A 请求晚于 B 返回；抽屉关闭后请求成功；保存期间切换租户；服务端提交后响应丢失；其他人先更新版本；用户保留草稿并重新读取。

纯函数可以验证状态转换和快照合并，组件测试需要验证 props 与事件，浏览器测试再覆盖焦点、输入保留和路由切换。下面的预期结果应在测试之前写清：旧结果被丢弃，当前失败可见，草稿可恢复，重复提交不增加副作用。

本篇的 TypeScript 和 watcher 片段用于说明设计，没有在 Vue 渲染器或真实后台接口中执行。可复用的部分是状态约定与测试顺序；引入项目时仍需用实际组件和服务端契约补齐集成验证。

页面复杂度最终体现为修改影响的范围

一个好的后台页面结构，让一次输入、一次请求和一次保存各有清楚的影响范围。路由描述正在看什么，快照描述已经知道什么，草稿描述准备改什么，提交回执描述实际发生了什么。职责分清以后，Vue 的响应式与 TypeScript 的约束才有稳定的落点。
