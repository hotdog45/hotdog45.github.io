Web3 交易状态设计：从钱包确认到链上事件对账

把登录签名、交易提交、区块确认与业务入账分开设计，讨论账户切换、日志去重、链重组和金额精度，避免把一个交易哈希误当成最终成功。

xq.Xiaofeng Qiao发布于 2026年10月23日本文暂时仅提供中文版本。

钱包弹窗关闭之后，业务才刚开始

用户点击确认，页面拿到交易哈希，随后显示“操作成功”。几秒后查询 receipt 发现执行失败；另一次 receipt 成功，服务端却没有识别到预期事件。两种情况下，“拿到 hash”都是真的，“业务已经完成”却都没有依据。

Web3 应用的难点之一，是让钱包、链节点、索引服务和业务页面对同一次操作使用一致的语言。这里按 2025 年的技术阶段讨论 EVM 应用状态设计，结合本站 ChainScope 的合成事件场景展开，不涉及真实钱包、资金或主网操作。

连接钱包与登录会话要分别失效

连接钱包表示应用可以通过 provider 与某条链交互，不等于服务端已经识别用户。登录签名用于证明某个地址在特定上下文中的控制权；交易签名则授权一项链上操作，两者不能共用一句模糊的“授权成功”。

若采用 SIWE，服务端需要校验消息格式、域名、URI、链 ID、时效、签名及自己发出的 nonce，并原子地消费 nonce，避免并发重放。签名者若是合约账户，还需要使用适合该类账户的验证机制，而不是只做 EOA 地址恢复。ERC-4361给出了登录消息与验证约定。

钱包切换账户后，旧页面里的草稿、查询缓存和当前会话需要重新核对；链切换后，地址相同也不能沿用另一条链的余额或合约配置。监听 accountsChanged、chainChanged 与断开事件只是入口，业务还要定义清理范围。EIP-1193规定了 provider 的请求与事件接口。

为每次操作保留三个身份

第一层是用户意图，例如一次表单提交产生的操作 ID；第二层是钱包提交后的交易哈希；第三层是链上事件的位置。它们并不是一一对应：用户可能拒绝签名，交易可能被替换，一笔交易也可能产生多个事件。

业务记录可以保留以下字段：

operationId
chainId + account + contract
transactionHash
blockNumber + blockHash + logIndex
observedState + updatedAt

operationId 用来关联界面与服务端流程，不能替代链上身份；事件去重可以采用包含链 ID、区块哈希、交易哈希和日志索引的复合键，并另外维护它是否属于当前规范链。只按交易哈希去重，会把同笔交易里的第二条有效事件丢掉。

接收日志时必须检查来自预期链与合约，并按匹配版本的 ABI 解码；事件名称相同不代表业务含义相同。代理合约升级后，还要知道历史事件使用哪个接口版本解释。

成功应该是一组可以解释的状态

界面可以区分：等待钱包确认、已提交、已进入区块、达到应用确认条件、执行失败、状态待核对。服务端另行记录业务对账是否完成。不要把节点超时或暂时查不到 receipt 直接写成链上失败。

用户意图 → 钱包确认 → 已提交 → 已入块 → 确认条件满足
                    ↘ 拒绝       ↘ 执行失败
                                     ↓
                              事件识别 → 业务对账

receipt 的 status 反映交易执行结果；即使执行成功，也仍要检查预期事件及其内容。确认数是应用策略，不能当成所有链统一的最终性保证。以太坊 JSON-RPC 支持的 safe、finalized 等区块标签，与“等若干块”也不是完全相同的概念，具体支持需以目标链和节点为准。JSON-RPC 参考及权益证明最终性说明可用于核对这些术语。

链重组要求修正观察，而不是再加一次余额

索引服务先看到了区块 A 的日志，之后同一高度变成区块 B。若只维护不断增长的确认次数，旧观察可能一直留在业务账本里。更可靠的扫描记录包括区块哈希、父哈希、检查点与一定范围的重扫。

发现分叉时，找到共同祖先，把失去规范链归属的观察标记为无效，再按新链重放。原始记录宜保留，便于解释为什么撤销；派生状态则根据仍有效的事件重算。不要在业务表中直接盲目“加一再减一”，否则重复回调或重扫很容易再次改变结果。

不可逆的外部动作尤其要谨慎安排。若事件触发发货，之后链上观察被撤销，数据库回滚并不能把货物收回。应用应按业务风险选择确认条件，并为异常保留人工核对入口；技术状态变更不是现实副作用的自动补偿。

金额的精度属于数据协议

RPC 中的整数金额应先按整数解析，再结合明确的 decimals 做显示。不要用 JavaScript Number 存储任意大的基础单位，也不要对所有资产写死 18 位小数。不同资产的基础单位不同，未完成单位换算前不能相加。

function formatUnits(raw, decimals) {
  if (!/^\d+$/.test(raw)) throw new Error('invalid integer')
  if (!Number.isInteger(decimals) || decimals < 0 || decimals > 36)
    throw new Error('unsupported decimals')
  const value = BigInt(raw)
  const scale = 10n ** BigInt(decimals)
  if (decimals === 0) return value.toString()
  const fraction = (value % scale).toString().padStart(decimals, '0')
  return `${value / scale}.${fraction}`
}

这里 0–36 是示例应用的支持范围，不是链协议对所有资产的上限。函数保持完整小数位，不处理展示舍入；产品若要只显示四位，应明确舍入规则并保留原值。负数、科学计数法和缺失 decimals 在此直接拒绝，避免它们被悄悄解释成另一种金额。

把异常做成可以重放的事件序列

验证一个索引流程，可以先准备确定性的日志夹具：同一日志收到两次；同笔交易有两条日志；相同高度区块哈希改变；旧分支撤销后重新扫描；节点返回超时；地址正确但链不匹配；大整数金额超出安全整数范围。

每组序列都检查最终派生状态，而不仅是处理函数是否返回成功。重放两次后事件集合应稳定，失效观察不能继续贡献业务结果，不同资产单位不能混算。测试网络再补节点分页、断线恢复和真实回执的集成演练，最后才讨论生产接入。

本站 ChainScope 案例可以编辑合成输入，观察精度、重复事件和确认条件的处理。它帮助展示工程规则，不连接真实 RPC；本文的金额函数另做本地断言，钱包签名、合约账户验证和实际链重组未在此集成运行。

让界面说出系统真正知道的事

“已提交”比无法证实的“已成功”更有用，“等待核对”也比随意归类失败更准确。一个可维护的 Web3 应用，需要把身份、签名意图、执行结果和业务状态分别留下证据，再用明确的转换关系连接起来。用户不必看到所有技术字段，但应该知道当前处于哪一步，以及下一步由谁推进。
