可重跑的Python自动化：断点、去重与失败账本

让批处理绑定输入快照，以稳定工作键恢复进度，隔离坏行并对账每个终态，而不是靠行号继续跑。

xq.Xiaofeng Qiao发布于 2026年10月23日本文暂时仅提供中文版本。

跑到第八十行，不代表下次从第八十一行继续

批量转换报表、整理资料或导入记录时，第一次成功并不难。真正的问题是：运行到第八十项退出后，输入文件又被别人插入了一行。保存下来的行号还有效吗？之前失败的三条记录，会不会被新一轮“完成数量”掩盖？

本文以2021年的Python3.9能力为回顾基线，讨论一份批处理怎样拥有可以对账的恢复过程。配套使用模拟CSV与临时SQLite数据库，2026年在Python3.9.6、SQLite3.54.0上实际运行；这个SQLite版本是复现环境，不代表当年的版本。

先冻结本次要处理的集合

脚本开始前，应把输入变成一个明确的批次：保存原始内容快照、内容摘要和格式版本。配套将原始CSV字节与SHA-256摘要存进manifest表，之后恢复前重新计算源文件摘要，不一致就停止，而不是默默接受新增行。

raw = Path(source).read_bytes()
digest = hashlib.sha256(raw).hexdigest()
previous = db.execute(
    "SELECT digest FROM manifest WHERE id=1"
).fetchone()
if previous and previous[0] != digest:
    raise ValueError("source changed; review the difference")

示例采用严格的字节级比较，连换行变化也会被识别。它简单但保守；若业务希望允许等价格式变化，可以建立版本化的规范化规则，不能在恢复时临时忽略差异。源文件有意更新时，应创建新批次或审阅差异后迁移状态，保留旧清单，不覆盖原始证据。

快照也不能随便保存敏感原文。实际输入包含个人资料时，需要限制访问与保留期限；摘要不是匿名化手段。本文只保存虚构工作键和数量。

工作键跟着业务，行号只负责定位错误

有效记录使用稳定job_id标识，而不是当前行号。文件排序变化不应该把同一项工作变成另一项；同一个工作键对应不同输入，则应报冲突，不能覆盖旧结果。

配套在执行前统计所有工作键。同批次出现重复键时，两条重复记录都拒绝，避免“第一条先写入、第二条才发现重复”产生顺序相关结果。行号仍有用途：缺少工作键的坏行只能以快照中的位置定位，但它不会获得一个可以执行的业务身份。

对于CSV，还要先验证表头、缺列和多余列，再检查数量的整数范围。不能因为某行转成字典，就认为格式已经正确。Python官方提供DictReader，但具体必填字段和业务类型仍需要程序负责。csv文档

坏行要隔离，不能让好行全部重做

配套把输入分为合法工作、确定性拒绝和暂时失败。非法数量、重复键和缺字段属于拒绝，不自动重试；依赖暂时失败则进入可重试账本，继续处理其他独立记录。

try:
    quantity = int(row.get("quantity") or "")
    if not 0 <= quantity <= 2**63 - 1:
        raise ValueError("quantity outside SQLite integer range")
except (ValueError, TypeError) as error:
    db.execute(
        "INSERT INTO failures(record_key,kind,reason) VALUES (?,?,?)",
        ("line:" + str(line), "rejected", str(error)),
    )
    counts["rejected"] += 1
    continue

完整实现还有结构和重复键检查。错误账本保留工作位置、错误分类和诊断，不把整个输入行、密钥或用户正文直接拼进日志。再次执行可以追加尝试记录，避免覆盖第一次失败原因；汇总时则以当前状态为准，不能把历史失败次数算成当前失败项数。

隔离也有前提：单项必须可以独立验收。若文件前半段定义了后半段所依赖的统一配置，继续运行可能扩大错误，应提升为批次级失败。哪些错误可以跳过，需要由业务约定。

成功回执只是恢复基础，不是整批状态

每个合法工作仍需要可靠的成功边界。示例的本地处理器把outputs和receipts放在同一SQLite事务，回执包含稳定键、输入摘要和结果。同键同输入读回旧结果，不重复写入；同键不同输入报冲突。这一小段基础用于让批次恢复能够信任“已经完成”的工作。

数据库连接使用显式事务控制，写入采用参数绑定。SQLite只有一个同时进行的写事务，批次过大时应考虑锁持有时间，而不把长时间解析和无关计算放在事务内。Python sqlite3、SQLite事务

本文不把本地事务推广为远端API的恰好执行一次保证。脚本的外部副作用需要另外的查询、幂等和未知结果处理；当前示例没有任何外部调用。

恢复时重新对账，不依赖一个乐观的游标

主循环对照冻结清单逐项读取回执。一次进程中断后，已经提交的工作被标为replayed，尚未执行的工作继续处理。输入没有变化，稳定工作键和回执就能定位进度，不必相信“上次大概到第几行”。

配套报告将done、rejected、retryable、pending与输入总行数对账。replayed是done的子集，不能再加一次。示例中三行输入有两项成功、一行坏数据，报告应是done2、rejected1、total3，而不是把“处理了三行”写成三项业务成功。

这里还区分两个结束判断：all_rows_terminal表示每行已经成功或明确拒绝，没有暂时失败；batch_complete则要求所有行成功。坏行被分类处理后，前者可以成立，后者仍为false。命名上的区别，会影响操作人员是否继续检查异常。

用中断和输入变化验证恢复协议

配套含十项测试，五项检验单项回执，五项检验批次：

  • 坏行进入账本，其他行正常完成。
  • 第一项提交后注入中断，重跑只恢复剩余工作。
  • 修改源文件后拒绝继续，既有结果没有增加。
  • 重复业务键全部被拒绝，不依赖文件顺序。
  • 暂时失败时不声称完整成功，恢复后仍保留坏行的待审状态。
python3 -m unittest -v

测试在本机通过，数据全部位于自动清理的临时目录。异常注入不等于断电实验，单操作员执行也不等于已经验证多进程竞争。磁盘满、数据库备份恢复和并发调度需要在目标环境补测；Python3.9已结束维护，新项目应选择仍受支持的解释器。

自动化的质量，体现在第二次运行

可靠脚本应该能解释本次输入是什么、每项工作的身份是什么、失败能否重试，以及剩余哪些内容尚未完成。输入快照稳定了分母，工作键稳定了身份，失败账本保留了恢复线索。只有这三者与成功回执结合，重新运行才是可审查的继续，而不是再赌一次。
